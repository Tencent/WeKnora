# 视频上传与公网部署故障经验

## 结论

这次故障不是单一的“上传进度显示错误”，而是两个问题叠加：

1. **业务链路缺陷**：同一个 HTTP 响应边界问题在不同阶段表现成列表超时和上传卡在 97%。
2. **发布链路失真**：本地工作区、Git 提交、构建上下文、镜像和生产容器不是同一份代码。部分修复虽然在本地通过，但没有进入 Git 提交或生产镜像，因此用户实际访问的仍是旧实现。

业务链路的两个直接症状是：

- Home 列表请求等待响应结束，最终被前端 30 秒超时判定为加载失败。
- 上传分片已经合并成功，界面进入 97%；随后详情请求等待 `response.text()` 完成，因无法确认响应结束而一直停在 97%。

最终根因是 `frontend/nginx.conf` 的 custom API 代理同时满足了以下条件：

1. 上游 Gin 使用 HTTP/1.1 chunked 响应。
2. Nginx 设置 `chunked_transfer_encoding off`，移除了分块传输。
3. Nginx 没有为这些动态响应补充 `Content-Length`。
4. 客户端只能依靠 `Connection: close` 判断响应结束；公网链路下连接关闭不可靠或延迟，导致浏览器看起来像“接口卡死”。

最终修复是恢复标准响应分帧，使 custom API 返回 `Transfer-Encoding: chunked` 或明确的 `Content-Length`，并保持持久连接。97% 只是等待详情响应体结束的表象，不应通过前端定时器掩盖底层问题。

发布链路还发现了一个独立根因：`.gitignore` 中没有路径边界的 `WeKnora` 规则，在本地忽略了 `internal/custom/client/weknora/`。本地 Go 构建可以读取这些文件，但 `git archive`、GitHub Actions 和 Docker 的干净提交构建上下文中没有它们，导致后端镜像报错：

```text
no required module provides package
github.com/Tencent/WeKnora/internal/custom/client/weknora
```

这解释了为什么“本地测试没问题”，但推送到 GitHub 或生产后仍不可用：本地测试验证的是带未跟踪文件的工作目录，生产构建验证的是提交快照，两者不是同一个输入。

## 故障时间线与证据链

| 阶段 | 当时看到的现象 | 实际问题 | 能证明问题的信号 |
| --- | --- | --- | --- |
| 分片合并 | 分片完成后页面停在 97% | complete 后的详情响应无法可靠结束 | 浏览器等待 `response.text()`；公网请求没有可靠响应边界 |
| 多轮前端修复 | 调整进度、轮询、封面状态后仍失败 | 修改的是等待期间的表象，没有修复 HTTP framing | 后端直连正常，经过生产 Nginx 后卡住 |
| 本地后端验证 | `go build` 和部分测试通过 | 本地目录含被 Git 忽略的 `internal/custom/client/weknora` | `git check-ignore -v` 能命中该目录，但 `git ls-tree` 查不到文件 |
| GitHub 发布 | 提交已经 push | 当时没有可确认成功的 workflow run，新 tag 镜像也不存在 | Actions run 查询为空，`docker manifest inspect <tag>` 失败 |
| 生产部署 | 服务器 Git 与本地提交不一致 | 生产工作树已分叉，Compose 又是现场未跟踪配置；Git HEAD 不能代表运行版本 | `git log --left-right`、Compose image、容器 `Config.Image` 三者不一致 |
| 最终定位 | 恢复 HTTP framing 后公网稳定 | 根因位于 Nginx 响应边界，而不是进度条、封面或分片合并 | 公网连续请求均有完整 JSON 和明确响应边界 |

上述证据说明，问题不是“某一次修复写错了”，而是诊断和发布都缺少一个能够覆盖真实生产链路的闭环。只要闭环中任一段没有被验证，继续修改代码就可能只是在修复未上线的代码。

## 为什么会反复出现

### 1. 把表象当成根因

先后把问题理解成“列表判定过严”“封面未完成”“公网丢包”“上传进度没有补到 100%”。这些现象都能在页面上看到，但都没有回答：

> 请求是否已经收到完整 HTTP 响应，客户端凭什么知道响应结束？

没有先检查响应头和响应边界，就容易继续修改状态机、轮询、封面和时长逻辑，修复范围不断扩大。

### 2. 阶段 3 的代理改动只修了一半

为减轻公网小包传输问题，`proxy_buffering` 从 `off` 改为 `on`，但 `chunked_transfer_encoding off` 被保留。缓冲解决了上游响应如何读取的问题，却没有解决 Nginx 如何向浏览器标记响应结束的问题。

因此“响应截断/卡住”的旧问题在另一种网络时序下继续存在。

### 3. 测试验证了状态码，没有验证 wire contract

此前的验证主要确认 `/`、ping、列表接口返回 200，甚至确认了 JSON 内容；但没有把以下条件作为验收门槛：

- 响应必须有 `Transfer-Encoding: chunked` 或 `Content-Length`。
- 不得同时出现无长度响应和 `Connection: close`。
- 请求必须经过公网入口和实际生产 UI 镜像，而不是只请求后端容器。
- 连续请求必须都能在短超时内收完整响应。

状态码 200 只代表服务端写出了响应，不代表浏览器已经拿到可完成解析的响应。

### 4. 本地代码、服务器 Git 和镜像是三套状态

服务器通过 `git am` 重算 hash 后，Git commit 与本地不同但内容可以相同；同时生产实际运行的是 Docker 镜像，而不是服务器工作树。只比对一个短 hash，或者只看服务器 Git HEAD，都不能证明线上运行了目标代码。

必须同时核对：

`本地提交内容 -> 构建上下文 -> 镜像 tag/digest -> Compose 声明 -> 实际容器 -> 公网行为`

### 5. 发布范围没有足够收敛

阶段修复、封面可见性、上传链路和生产配置交错发布时，出现问题后很难判断是哪一层引入回归。此次最终修复只改 Nginx，只更新 UI 镜像，backend 保持原镜像，才使根因验证和回滚边界清晰。

### 6. 本地测试验证了脏工作区，不是提交快照

本地目录里存在未跟踪或被忽略的源码时，`go test`、`go build`、Vite 构建都能读取这些文件；GitHub Actions 和基于 `git archive` 的生产构建却只能看到已提交文件。因此“本地构建通过”不能推出“该 commit 可构建”。

这次被漏掉的是 `internal/custom/client/weknora/*.go`。修复提交 `1ab7d69d` 增加了 `.gitignore` 例外并正式提交这些文件。以后必须从目标 commit 的干净快照构建，而不是直接把开发目录当作发布输入。

### 7. 把 push 成功误当成发布成功

`git push` 成功只证明远程分支收到了 commit，不证明以下任何一项成立：

- CI 被触发并通过。
- 前端和后端镜像均已生成。
- 镜像 tag 对应目标 commit。
- 生产已经拉取并启动该镜像。

当时目标镜像不存在，生产只能继续运行旧镜像。继续修改代码并反复 push，不会自动改变线上行为。

### 8. 没有先建立能对原始症状变红的反馈闭环

早期检查多为“接口返回 200”“后端健康”“页面能打开”，这些信号无法捕获“浏览器一直等不到响应结束”这一具体故障。没有能在原始故障上变红的检查，就无法判断每次修改究竟修复了原始问题，还是只改变了附近行为。

本次应采用的最小反馈信号是：通过真实生产入口请求 custom API，在短超时内收完整 JSON，并检查响应拥有明确 framing；上传闭环则必须完成 `init -> parts -> complete -> detail -> list -> play`，不能以进度条到达某个数字作为通过标准。

### 9. 生产现场状态没有单一事实来源

生产服务器同时存在分叉的 Git 分支、未跟踪的 `docker-compose.cloud.yml`、本地镜像和注册表镜像。直接 `git pull` 可能覆盖现场配置，只看 Git HEAD 又不能说明容器实际运行了什么。

生产运行版本应以不可变镜像 tag/digest 和容器 `Config.Image` 为准，Git 工作树只作为辅助信息。现场 Compose 必须备份，但模板、变量约束和发布规则要在仓库中维护。

### 10. 应急部署和正式发布边界不清

为恢复服务，可以在生产机从确定的 commit 构建本地镜像，但这只能作为应急措施。只存在于单台服务器的镜像无法支持灾备重建，也不能证明 Docker Hub 中存在相同产物。

应急恢复后必须补做正式发布：CI 从提交快照构建、推送不可变 tag、记录 digest，并验证另一台干净机器能够拉取。否则服务器磁盘损坏或迁移时，同一版本无法重现。

## 五个为什么

1. **为什么上传卡在 97%？** 因为 complete 后的详情请求没有结束，前端仍在等待完整响应体。
2. **为什么详情请求没有结束？** 因为 Nginx 关闭 chunked 后没有补充 `Content-Length`，公网客户端无法可靠判断动态响应边界。
3. **为什么多轮修改仍没有解决？** 因为修改集中在进度、轮询、封面和状态机，没有用真实公网响应完成作为反馈信号。
4. **为什么部分正确修复也没有立即生效？** 因为本地、Git 提交、镜像和生产容器版本不一致，且目标镜像并未成功发布。
5. **为什么版本会不一致？** 因为缺少“干净提交构建 + CI 成功 + 镜像存在 + Compose 指向 + 容器实际镜像 + 公网闭环”的强制发布门禁。

## 开发阶段注意事项

### 先建立最小复现

遇到“加载很慢、最终失败、进度卡住”时，先固定一个能复现用户症状的检查：

```bash
curl --http1.1 --max-time 5 -D - -o /tmp/videos.json \
  http://<入口>/api/custom/videos
```

同时记录状态码、`Content-Length`、`Transfer-Encoding`、`Connection`、响应体大小和耗时。对于浏览器卡在某个进度值的问题，定位到对应的 `fetch`/`response.text()` 调用，而不是先改进度数字。

检查必须能够在旧实现上稳定失败，在修复后稳定通过。仅检查进程未崩溃、状态码为 200 或健康接口正常，都不属于针对本故障的有效反馈信号。

### 先画请求链路，再改代码

确认请求经过的实际路径：

```text
Browser -> 公网 Nginx -> custom-backend -> PostgreSQL/MinIO
```

分别确认：后端直连是否正常、Nginx 代理后是否正常、公网访问是否正常。只有公网链路失败而后端直连成功时，才把注意力集中到 Nginx 和网络边界。

### 固定不变量

- `multipart complete` 成功后，视频源文件和播放地址必须已经可用。
- `cover_url`、`thumbnail_url`、`duration_seconds` 是增强字段，不是文件可用的前置条件。
- custom API 的动态响应必须有明确的 HTTP 响应边界。
- 详情、列表和上传完成响应的 `file_url/play_url` 语义必须一致。
- 前端状态只能反映真实阶段；不能用“请求超时后当成功”替代协议修复。

### 控制变更范围

一个故障只保留一个根因修复。若根因在代理层，优先修代理层；不要同时改列表过滤、上传状态、轮询间隔和 UI 文案。确需兼容性兜底时，必须证明它解决的是独立故障，并单独测试。

### 从提交快照验证可构建性

发布前先证明依赖文件都在 Git 中：

```bash
git check-ignore -v internal/custom/client/weknora/client.go || true
git ls-tree -r --name-only HEAD internal/custom/client/weknora
git status --short --ignored
```

然后使用隔离 worktree 或 `git archive` 生成构建上下文。禁止直接用含有未提交文件、被忽略源码或旧 `dist` 的开发目录证明“生产可构建”。

```bash
release_dir="$(mktemp -d)"
git archive HEAD | tar -x -C "$release_dir"
docker build -f "$release_dir/docker/Dockerfile.custom-backend" "$release_dir"
```

如果干净快照失败而开发目录成功，应先比较 `git ls-files`、`git status --ignored` 和 Docker build context，不要继续修改业务逻辑。

## 测试验证阶段注意事项

### 必测四层

1. **代码层**：针对根因写回归测试，测试必须在旧实现上失败、在新实现上通过。
2. **容器层**：构建实际生产镜像，执行 `nginx -t`，确认模板变量替换后的配置正确。
3. **入口层**：通过 Nginx 端口请求，而不是只请求 backend 容器。
4. **公网层**：使用真实公网地址，验证与用户相同的链路和协议。

另外增加一项发布输入检查：测试和镜像构建必须基于同一个 commit 快照。若测试运行在开发工作区、镜像构建运行在 GitHub checkout，两者不构成同一次验证。

### HTTP 响应验收

对 `/api/custom/ping`、`/api/custom/videos`、详情和上传完成接口至少检查：

- HTTP 状态码为 200。
- `Content-Length` 或 `Transfer-Encoding: chunked` 至少存在一个。
- 无长度响应不能依赖 `Connection: close`。
- 响应体是完整 JSON，能够被 `JSON.parse` 解析。
- 连续 10 次请求在明确的短超时内完成。

### 上传验收

使用真实视频完成一条闭环：

1. init 成功并记录 `video_id`。
2. 所有分片上传成功。
3. complete 成功。
4. 详情请求完成并返回可播放地址。
5. 列表在 3 秒内出现视频。
6. 刷新页面后视频仍存在。
7. 封面或时长失败时，列表项仍保留且播放入口可用。

上传进度数字不是验收信号；`complete`、详情、列表和播放地址才是验收信号。

## 部署阶段注意事项

### 发布前

- 记录唯一发布 commit 和镜像 tag。
- UI 改动只构建 UI 镜像；backend 未改就不重新构建或切换 backend。
- 使用 `linux/amd64` 构建并检查镜像架构。
- 从干净的提交工作树构建，避免把 `.env`、未提交文件、临时二进制或旧 `dist` 带入镜像。
- 生产 Compose 和 `.env` 必须先备份，并保留可直接回滚的旧镜像。
- 查询目标 commit 的 CI run，确认必需 job 全部成功；“没有 run”必须按失败处理。
- 使用 `docker manifest inspect <repository>:<tag>` 确认注册表中目标镜像真实存在。
- 记录镜像 digest；不能只记录可能被覆盖的 tag。

建议把下面的检查做成发布脚本的硬门禁：

```bash
commit8="$(git rev-parse --short=8 HEAD)"
test -z "$(git status --porcelain)"
git ls-tree -r --name-only HEAD internal/custom/client/weknora \
  | grep -q 'client.go'
docker manifest inspect "<registry>/vidsage-ui:custom-${commit8}" >/dev/null
docker manifest inspect "<registry>/vidsage-custom-backend:custom-${commit8}" >/dev/null
```

若某次发布只修改 UI，可以明确跳过后端镜像检查，但必须在发布记录中写明后端保持的 tag/digest。

### 切换时

```bash
sudo docker load -i <image>.tar.gz
sudo docker compose -p vidsage \
  -f docker-compose.yml -f docker-compose.cloud.yml config --quiet
sudo docker compose -p vidsage \
  -f docker-compose.yml -f docker-compose.cloud.yml up -d frontend
```

只更新目标服务，避免无关服务滚动重启。切换完成后核对 Compose 中的 tag 和容器实际 `Config.Image` 完全一致。

```bash
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml config --images
sudo docker inspect -f '{{.Name}} {{.Config.Image}} {{.Image}}' \
  WeKnora-frontend vidsage-custom-backend
```

生产 Git 分支发生分叉或 Compose 是未跟踪现场文件时，不得为了“对齐版本”直接执行破坏性 reset 或覆盖配置。先备份 Compose，再使用明确镜像 tag 更新目标服务。

### 切换后

按顺序验证：

1. 容器状态和健康检查。
2. `/` 和 `/api/custom/ping`。
3. `/api/custom/videos` 响应头和完整 JSON。
4. 公网连续请求。
5. 真实上传闭环。

任何一项失败，立即使用备份 Compose 和旧镜像回滚；不要在生产容器内临时改配置后继续观察。

## 发布完成标准

只有以下链路全部成立，才算修复完成：

```text
根因复现为红
-> 单一根因修复
-> 回归测试为绿
-> 目标 commit 的干净快照可构建
-> CI run 成功且注册表镜像存在
-> 镜像内配置正确
-> Compose 声明与容器实际镜像一致
-> 公网响应边界正确
-> 真实上传闭环通过
-> 记录 commit、镜像、容器和回滚点
```

任何箭头断开，都只能称为“代码已修改”或“应急恢复”，不能称为“生产修复完成”。
