# 知识库问答反馈归因与权重自适应

WeKnora 的知识库问答反馈功能将用户的点赞/点踩行为从"仅评价单条回复"升级为"归因到回复所引用的每一个知识库片段"，并基于片段好评率自动调整其召回权重，形成 **用户反馈 → 片段统计 → 权重调整 → 检索优化** 的闭环。

## 一、为什么需要这个功能

### 问题背景

在引入本功能之前，WeKnora 的知识库问答系统存在以下痛点：

1. **反馈无法沉淀到知识源头**：用户对问答回复的点赞/点踩仅停留在"这条回答好不好"的层面，系统无法知道是哪个知识库片段导致了好/坏体验。一个低质片段可能被反复引用、反复差评，却始终不会被识别和优化。

2. **片段质量缺乏量化指标**：知识库管理员只能通过"被检索次数"等间接指标判断片段价值，无法直接获取用户对片段的真实评价（好评率、点踩原因分布等），难以精准定位需要优化的内容。

3. **检索排序对质量"无感知"**：无论一个片段被用户差评多少次，它在后续检索中的排序权重始终不变，低质片段持续占据召回高位，形成恶性循环。

4. **缺少人工干预入口**：管理员无法重置异常的反馈数据、无法手动调整片段权重、无法查看权重变更历史，运维手段不足。

### 核心价值

本功能通过将用户反馈归因到知识库片段并驱动权重自适应，实现：

- **反馈闭环**：用户每次点赞/点踩都会自动归因到回复引用的所有片段，沉淀为片段级的累计统计数据。
- **质量可视化**：后台可按片段查看好评率、点踩原因聚合、关联会话数等，支持按好评率筛选低质片段。
- **检索自优化**：好评率高的片段自动获得更高召回权重（排序靠前），差评片段自动降权（减少命中），系统随用户反馈持续自我优化。
- **运维可审计**：权重变更全程记录日志，管理员可手动重置或调整，触发来源清晰可查。

## 二、整体方案设计

### 设计原则

| 原则 | 说明 |
|------|------|
| **用户无感知** | 前端交互不变，用户仍只在回复气泡底部点赞/点踩，无需感知背后的片段关联逻辑 |
| **自动归因** | AI 生成回复时已记录引用的片段 ID，用户评价时系统自动将评价绑定到所有引用片段 |
| **增量更新** | 评价提交时计算 delta（前一次评价 vs 新评价），只更新差量，避免全量重算 |
| **best-effort 权重** | 检索时若查不到片段权重，默认 1.0（无影响），不阻塞检索流程 |
| **可配置阈值** | 权重调整的阈值、升降权幅度均可通过 `FeedbackThresholds` 配置 |

### 数据流全景

```
┌─────────────────────────────────────────────────────────────────┐
│                        用户交互层                                │
│  用户在回复气泡底部点击 点赞 / 点踩(选原因) / 取消               │
└──────────────────────────┬──────────────────────────────────────┘
                           │ POST /api/v1/feedback
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                     FeedbackService                              │
│  1. 获取 assistant message（含 KnowledgeReferences JSON）       │
│  2. EnsureChunkRefs() → 展开为 message_chunk_refs 规范化表      │
│  3. 获取该消息引用的所有 chunk IDs                               │
│  4. 获取用户之前的评价（计算 delta）                             │
│  5. 对每个 chunk：                                               │
│     ├── 增量更新 like_count / dislike_count                     │
│     ├── 重算 approval_rate = like / (like + dislike)            │
│     ├── 重算 recall_weight（基于阈值）                           │
│     ├── 更新 needs_optimization 标志                             │
│     └── 权重变化 → 写入 chunk_weight_logs                       │
│  6. UpsertFeedback() → 持久化评价记录                           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                    后续知识库检索                                │
│  HybridSearch → fuseOrDeduplicate (RRF融合)                     │
│     → applyRecallWeights()                                       │
│        每个 chunk 的 score *= recall_weight → 重新排序          │
└─────────────────────────────────────────────────────────────────┘
```

### 权重调整规则

基于片段好评率（`approval_rate = like_count / (like_count + dislike_count)`）自动调整：

| 好评率区间 | 召回权重 | 效果 | 备注 |
|-----------|---------|------|------|
| ≥ 80% | 1.5（提升） | 优先命中、排序靠前 | `BoostThreshold` |
| 50% ~ 80% | 1.0（不变） | 维持现状 | `ReduceThreshold` ~ `BoostThreshold` |
| < 50% | 0.5（降低） | 减少命中概率 | < `ReduceThreshold` |
| < 30% | 同上 + 标记"待优化" | 后台提醒人工整改 | < `OptimizeThreshold` |

**门槛保护**：总反馈数（点赞+点踩）少于 `MinFeedbackCount`（默认 3）时不触发权重调整，避免新片段因单次差评被误降权。

## 三、数据模型

### chunks 表扩展字段

在现有 `chunks` 表上新增 6 个字段，用于存储片段级的反馈统计和召回权重：

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `like_count` | INTEGER | 0 | 累计点赞数 |
| `dislike_count` | INTEGER | 0 | 累计点踩数 |
| `approval_rate` | DOUBLE PRECISION | 0 | 好评率 = like / (like + dislike) |
| `recall_weight` | DOUBLE PRECISION | 1.0 | 召回权重乘子（检索时乘到分数上） |
| `needs_optimization` | BOOLEAN | false | 是否需要人工优化（好评率极低时标记） |
| `feedback_updated_at` | TIMESTAMP | NULL | 反馈计数最后一次重算时间 |

对应 Go 结构体字段（`internal/types/chunk.go`）：

```go
LikeCount          int        `json:"like_count"          gorm:"default:0"`
DislikeCount       int        `json:"dislike_count"       gorm:"default:0"`
ApprovalRate       float64    `json:"approval_rate"       gorm:"default:0"`
RecallWeight       float64    `json:"recall_weight"       gorm:"default:1.0"`
NeedsOptimization  bool       `json:"needs_optimization"  gorm:"default:false"`
FeedbackUpdatedAt  *time.Time `json:"feedback_updated_at,omitempty"`
```

### message_feedback 表

记录用户对某条 assistant 消息的评价。一个 `(user_id, message_id)` 对只有一条记录，切换评价类型时 upsert 覆盖。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) | UUID 主键 |
| `tenant_id` | BIGINT | 租户 ID |
| `user_id` | VARCHAR(512) | 用户 ID |
| `session_id` | VARCHAR(36) | 会话 ID |
| `message_id` | VARCHAR(36) | 被评价的消息 ID |
| `feedback_type` | VARCHAR(16) | `like` / `dislike` / `none` |
| `reason` | VARCHAR(64) | 点踩原因码（如 `irrelevant`） |
| `reason_detail` | TEXT | 点踩补充说明（自由文本） |
| `created_at` | TIMESTAMP | 创建时间 |
| `updated_at` | TIMESTAMP | 更新时间 |

唯一索引：`(user_id, message_id)` — 确保一个用户对一条消息只有一条评价记录。

### message_chunk_refs 表

问答回复与知识库片段的规范化关联表。从 `Message.KnowledgeReferences` JSON 字段惰性展开，用于高效 SQL JOIN 查询（如"这个片段被多少个会话引用过"、"这个片段的点踩原因分布"）。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) | UUID 主键 |
| `tenant_id` | BIGINT | 租户 ID |
| `message_id` | VARCHAR(36) | 关联的消息 ID |
| `session_id` | VARCHAR(36) | 关联的会话 ID |
| `chunk_id` | VARCHAR(36) | 引用的片段 ID |
| `knowledge_id` | VARCHAR(36) | 知识文档 ID |
| `kb_id` | VARCHAR(36) | 知识库 ID |
| `created_at` | TIMESTAMP | 创建时间 |

唯一索引：`(message_id, chunk_id)` — 幂等去重，同一条消息不会重复关联同一片段。

### chunk_weight_logs 表

片段召回权重的变更审计日志，每次权重变化都记录前后状态和触发来源。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(36) | UUID 主键 |
| `tenant_id` | BIGINT | 租户 ID |
| `chunk_id` | VARCHAR(36) | 片段 ID |
| `old_weight` | DOUBLE | 变更前权重 |
| `new_weight` | DOUBLE | 变更后权重 |
| `old_approval_rate` | DOUBLE | 变更前好评率 |
| `new_approval_rate` | DOUBLE | 变更后好评率 |
| `old_like_count` | INTEGER | 变更前点赞数 |
| `new_like_count` | INTEGER | 变更后点赞数 |
| `old_dislike_count` | INTEGER | 变更前点踩数 |
| `new_dislike_count` | INTEGER | 变更后点踩数 |
| `trigger_type` | VARCHAR(32) | `user_feedback` / `admin_reset` / `admin_manual` |
| `trigger_detail` | TEXT | 触发详情（如点踩原因、管理员 ID） |
| `created_at` | TIMESTAMP | 创建时间 |

### Go 类型定义

所有新增类型定义在 `internal/types/feedback.go`：

```go
// 评价类型
type FeedbackType string
const (
    FeedbackLike     FeedbackType = "like"
    FeedbackDislike  FeedbackType = "dislike"
    FeedbackNone     FeedbackType = "none"   // 取消评价
)

// 权重变更触发类型
type WeightLogTriggerType string
const (
    WeightTriggerUserFeedback WeightLogTriggerType = "user_feedback" // 用户评价触发
    WeightTriggerAdminReset   WeightLogTriggerType = "admin_reset"   // 管理员重置
    WeightTriggerAdminManual  WeightLogTriggerType = "admin_manual"  // 管理员手动设置
)
```

**权重计算函数**（核心算法）：

```go
// ComputeWeight 根据好评率和阈值计算召回权重和待优化标志
func ComputeWeight(likeCount, dislikeCount int, thresholds *FeedbackThresholds) (weight float64, needsOptimization bool) {
    total := likeCount + dislikeCount
    if total < thresholds.MinFeedbackCount {
        return 1.0, false  // 反馈不足，不调整
    }
    approvalRate := float64(likeCount) / float64(total)
    needsOptimization = approvalRate < thresholds.OptimizeThreshold
    switch {
    case approvalRate >= thresholds.BoostThreshold:
        return thresholds.BoostWeight, needsOptimization    // ≥80% → 1.5
    case approvalRate < thresholds.ReduceThreshold:
        return thresholds.ReduceWeight, needsOptimization   // <50% → 0.5
    default:
        return 1.0, needsOptimization                        // 50%~80% → 1.0
    }
}
```

### 仓库层（Repository）

#### feedback.go（`internal/application/repository/feedback.go`）

**核心方法：`EnsureChunkRefs`**

为什么需要这个方法：`Message.KnowledgeReferences` 是一个 JSON 字段，存储了回复引用的所有 `SearchResult`（含 chunk ID）。但 JSON 字段无法高效做 SQL JOIN 查询（如"这个片段被多少会话引用过"）。`EnsureChunkRefs` 将 JSON 展开为规范化的 `message_chunk_refs` 表行，惰性执行（首次评价该消息时触发），幂等设计（重复调用不会产生重复行）。

```go
func (r *feedbackRepository) EnsureChunkRefs(ctx context.Context, msg *types.Message) error {
    // 1. 从 msg.KnowledgeReferences 提取 chunk ID + 元数据
    // 2. 查询已存在的关联行，跳过已关联的 chunk
    // 3. 批量插入新的关联行
}
```

**核心方法：`AggregateDislikeReasonsByChunk`**

通过 SQL JOIN `message_feedback` ↔ `message_chunk_refs` 聚合某个片段的点踩原因分布：

```sql
SELECT mf.reason AS reason, COUNT(*) AS count
FROM message_feedback mf
INNER JOIN message_chunk_refs mcr ON mf.message_id = mcr.message_id
WHERE mcr.tenant_id = ? AND mcr.chunk_id = ?
  AND mf.feedback_type = 'dislike' AND mf.reason <> ''
GROUP BY mf.reason
ORDER BY count DESC
```

**核心方法：`UpsertFeedback`**

使用 GORM 的 `clause.OnConflict` 实现 upsert，冲突列是 `(user_id, message_id)` 唯一索引：

```go
r.db.Clauses(clause.OnConflict{
    Columns:   []clause.Column{{Name: "user_id"}, {Name: "message_id"}},
    DoUpdates: clause.AssignmentColumns([]string{"feedback_type", "reason", "reason_detail", "updated_at"}),
}).Create(fb)
```

#### chunk_weight_log.go（`internal/application/repository/chunk_weight_log.go`）

分页查询权重变更日志，支持按片段 ID 筛选或查看全租户日志。结果按 `created_at DESC` 排序（最新变更在前）。

#### chunk_feedback_stats.go（`internal/application/repository/chunk_feedback_stats.go`）

分页查询片段反馈统计，支持：
- 按 `knowledge_base_id` 筛选
- 按 `min_approval` / `max_approval` 好评率范围筛选（用于"查看低质片段"）
- 按 `needs_optimization = true` 筛选（仅看待优化片段）
- 结果排序：`needs_optimization DESC, approval_rate ASC, updated_at DESC`（最需要关注的排最前）

### 服务层（Service）

**文件**：`internal/application/service/feedback.go`

这是整个功能的核心业务逻辑层。

#### 构造函数

```go
func NewFeedbackService(
    db *gorm.DB,
    feedbackRepo  interfaces.FeedbackRepository,
    weightLogRepo interfaces.ChunkWeightLogRepository,
    statsRepo     interfaces.ChunkFeedbackStatsRepository,
    chunkRepo     interfaces.ChunkRepository,
    messageRepo   interfaces.MessageRepository,
) interfaces.FeedbackService
```

依赖注入了 5 个仓库 + 1 个 DB 连接 + 默认阈值配置。

#### 核心方法：`SubmitFeedback`

完整流程：

```
1. 从 context 获取 tenant_id 和 user_id
2. 获取被评价的 assistant message（验证角色为 assistant）
3. EnsureChunkRefs() — 确保片段关联已持久化
4. ListChunkIDsByMessage() — 获取该消息引用的所有 chunk IDs
5. GetFeedback() — 获取用户之前的评价（用于计算 delta）
6. 如果 feedback_type == "none"（取消评价）：
   ├── reverseFeedbackOnChunks() — 撤销之前评价对各 chunk 的影响
   └── DeleteFeedback() — 删除评价记录
7. 否则（like / dislike）：
   ├── UpsertFeedback() — 持久化新评价
   └── applyFeedbackDelta() — 对每个 chunk 应用增量更新
```

#### 核心方法：`applyFeedbackDelta`

对每个被引用的 chunk 执行增量更新：

```
对每个 chunkID:
  1. 获取 chunk 当前状态（oldLike, oldDislike, oldWeight）
  2. 撤销旧评价的贡献（prev == like → likeCount--；prev == dislike → dislikeCount--）
  3. 施加新评价的贡献（new == like → likeCount++；new == dislike → dislikeCount++）
  4. Clamp 到非负
  5. 重算 approval_rate = ComputeApprovalRate(like, dislike)
  6. 重算 recall_weight + needs_optimization = ComputeWeight(like, dislike, thresholds)
  7. UpdateChunk() — 持久化
  8. 如果 weight 变化 → CreateLog() — 写审计日志
```

**为什么用 delta 而不是全量重算**：一条消息可能引用多个 chunk，每次评价只需要更新被引用的 chunk。增量方式避免了全表扫描和全量重算，性能更优。

#### 核心方法：`AdminResetChunkFeedback`

管理员重置片段反馈数据：将 `like_count`、`dislike_count`、`approval_rate`、`recall_weight`、`needs_optimization` 全部恢复为默认值，并记录 `admin_reset` 类型的权重日志。

#### 核心方法：`AdminSetChunkWeight`

管理员手动设置片段召回权重（0~10 范围），记录 `admin_manual` 类型的权重日志。

## 六、检索权重集成

**文件**：`internal/application/service/knowledgebase_search_fusion.go`

这是将用户反馈与检索管道打通的关键集成点。

### 为什么在这里集成

WeKnora 的混合检索流程为：

```
HybridSearch
  → retrieveFromStores()     // 向量检索 + 关键词检索
  → classifyRetrievalResults() // 分类
  → fuseOrDeduplicate()       // RRF 融合 + 去重
  → [新增] applyRecallWeights() // 应用反馈权重 ← 集成点
  → applyFAQPostProcessing()   // FAQ 后处理
  → MatchCount 截断
  → processSearchResults()     // 构造 SearchResult
```

在 RRF 融合之后、TopK 截断之前应用权重，这样：
1. 权重作用于已融合的统一分数，不会被后续融合覆盖
2. 权重影响最终 TopK 选择，高质片段更容易进入上下文

### 实现代码

```go
func (s *knowledgeBaseService) applyRecallWeights(
    ctx context.Context,
    results []*types.IndexWithScore,
) []*types.IndexWithScore {
    // 1. 收集所有 chunk ID（去重）
    chunkIDs := collectUniqueChunkIDs(results)

    // 2. 批量查询片段的 RecallWeight
    //    使用 ListChunksByIDOnly（不按租户过滤，因为搜索可能跨共享 KB）
    chunks, err := s.chunkRepo.ListChunksByIDOnly(ctx, chunkIDs)
    if err != nil {
        // best-effort：查询失败不阻塞检索，权重默认 1.0
        return results
    }

    // 3. 构建 chunkID → weight 映射
    weightMap := make(map[string]float64)
    for _, ch := range chunks {
        weightMap[ch.ID] = ch.RecallWeight  // 默认 1.0
    }

    // 4. 乘权重到分数上，并重新排序
    for _, r := range results {
        if w := weightMap[r.ChunkID]; w != 1.0 {
            r.Score *= w
        }
    }
    slices.SortFunc(results, sortByScoreDesc)

    return results
}
```

**调用位置**（`knowledgebase_search.go`）：

```go
deduplicatedChunks := fuseOrDeduplicate(ctx, vectorResults, keywordResults, retrievalCfg)

// 应用基于用户反馈的召回权重
deduplicatedChunks = s.applyRecallWeights(ctx, deduplicatedChunks)

kb.EnsureDefaults()
// ... 后续 FAQ 后处理 + TopK 截断
```

## 九、关键设计决策

### 1. 为什么复用 `Message.KnowledgeReferences` 而不是新建关联表

`Message.KnowledgeReferences` 是一个 JSON 字段，已经在 AI 生成回复时存储了引用的所有 `SearchResult`（含 chunk ID）。我们**没有修改聊天管道代码**来在消息创建时写入关联表，而是在用户首次评价该消息时**惰性展开** JSON 为规范化表行（`EnsureChunkRefs`）。

**优势**：
- 零侵入：不修改复杂的聊天管道（streaming、agent、RAG 等流程）
- 幂等：重复调用安全，唯一索引 `(message_id, chunk_id)` 去重
- 按需：只有被评价的消息才会展开关联，减少不必要的写入

### 2. 为什么用 delta 更新而不是全量重算

一条消息可能引用 5~10 个 chunk，每次评价只影响这些 chunk。delta 方式：
- 只读取/更新被引用的 chunk（O(引用数) vs O(全部反馈数)）
- 避免了"先减去旧评价再全量重算"的复杂逻辑
- 并发安全：每个 chunk 独立更新，不存在跨 chunk 事务

### 3. 为什么设置 `MinFeedbackCount` 门槛

新片段或冷门片段可能只有 1~2 条反馈。如果单次差评就触发降权，会导致：
- 新内容因初始差评被埋没，永远无法被检索到
- 少量样本不代表真实质量

`MinFeedbackCount = 3` 确保权重调整基于足够的反馈样本。

### 4. 为什么用 best-effort 权重应用

检索是核心流程，不能因反馈功能的引入而变得脆弱。`applyRecallWeights` 在查询 chunk 权重失败时静默降级为权重 1.0（无影响），不阻塞检索、不返回错误。

### 5. 为什么 GORM 表名需要 `TableName()` 覆盖

GORM 默认将结构体名复数化作为表名（`MessageFeedback` → `message_feedbacks`），但迁移创建的表名是 `message_feedback`（单数）。通过显式 `TableName()` 方法覆盖，确保 GORM 查询使用正确的表名。

## 十、扩展指南

### 调整权重阈值

修改 `internal/types/feedback.go` 中的 `DefaultFeedbackThresholds()`：

```go
func DefaultFeedbackThresholds() *FeedbackThresholds {
    return &FeedbackThresholds{
        BoostThreshold:    0.75,  // 降低提升门槛
        ReduceThreshold:   0.4,   // 更早降权
        OptimizeThreshold: 0.25,
        BoostWeight:       2.0,   // 更强的提升效果
        ReduceWeight:      0.3,   // 更强的降权效果
        MinFeedbackCount:  5,     // 需要更多样本
    }
}
```

### 新增点踩原因

1. 在前端 `botmsg.vue` 的 `t-radio-group` 中新增 `<t-radio value="new_reason">` 选项
2. 在 i18n 文件中添加对应翻译
3. 后端无需修改 — `reason` 字段是自由字符串，任意原因码都能存储和聚合

### 支持嵌入模式（Embed Chat）

当前反馈功能仅在主聊天界面（`botmsg.vue`）实现。如需在嵌入模式中支持，需要：
1. 在 `EmbedUserMessage.vue` 或对应的 bot 消息组件中添加相同的点赞/点踩 UI
2. 在 `RegisterEmbedPublicRoutes` 中添加嵌入模式的反馈端点（需使用 embed session 的认证方式）

### 接入系统设置动态阈值

当前阈值通过 `DefaultFeedbackThresholds()` 硬编码。如需运行时动态配置：
1. 在 `system_settings` 表中新增 `feedback_thresholds` 键
2. 在 `FeedbackService` 中注入 `SystemSettingService`
3. `GetThresholds()` 从系统设置读取，`DefaultFeedbackThresholds()` 作为 fallback
