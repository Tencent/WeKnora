## 1. 四分支模型与流向图（PDF 5.1 P29）

```
 upstream/main      (腾讯官方仓库 · 只读同步，从不直接修改)
       ↓  merge --ff-only  (每周同步一次或发版前)
  origin/main         (自己 Fork 的官方镜像 · 保持与 upstream 完全一致)
       ↓  merge main  (官方代码确认无误后合入二开主线)
 custom/main         (二开长期维护的发布基线 · 服务器部署 100% 用此分支)
       ↓  switch -c feat/*  (每次功能开发从此切临时分支)
  feat/功能名称       (开发分支 · feat/* / fix/* 两类命名)
       ↓  PR（人工审查）
 custom/main         (合并后，feature 分支从远端删除)
```

**分支命名规范**（PDF 5.1 P26）：

| 前缀 | 含义 | 示例 |
|------|------|------|
| `feat/*` | 新增功能 / 页面 / 组件 / API | `feat/videohub-batch2` · `feat/wiki-export` |
| `fix/*` | 修复 bug / 回归问题 | `fix/wiki-save-error` · `fix/login-token-storage` |
| `chore/*` | 纯工程化改动（不影响运行） | `chore/bump-weknora-v0.7.3` · `chore/sync-upstream` |

## 2. 5.1 代码提交分支（11 步标准流程 · PDF 5.1）

> 每一步执行后都要按「期望输出」列做检查；**任何一步不匹配必须停住先排查**。

### 2.1 清空当前工作区（P25 §1）

**目标**：防止旧修改混入同步流程；把未提交内容先保存到独立备份或 stash。

```bash
# 1. 查看当前分支 & 未提交
git rev-parse --abbrev-ref HEAD        # 期望：custom/main 或 feature分支
git status --short --branch             # 期望：干净（或先处理未提交）

# 2. 未提交修改 → stash（-u 含未跟踪新文件）
git stash push -u -m "wip: backup before upstream sync $(date +%Y%m%d)"
git stash list                          # 可以看到刚存的 stash@{0}
git status --short --branch             # 期望：干净
```

### 2.2 同步腾讯官方代码（P25 §2）

**目标**：本地 `main` 与腾讯官方 `upstream/main` **完全一致**。

```bash
# 1. 拉官方最新（含删除的引用）
git fetch upstream --prune

# 2. main ← upstream/main（必须 fast-forward，不允许产生 merge commit）
git switch main
git merge --ff-only upstream/main       # ✗ 非 ff 说明本地 main 有脏提交，应重做 clone 或 reset

# 3. 推送自己 Fork 的 main
git push origin main

# 4. 检查是否完全一致：输出应为 0  0
git rev-list --left-right --count upstream/main...main
# 期望：0  0        （左=upstream多的commits，右=本地多的commits）
```

### 2.3 更新二开主线（P26 §3）

**目标**：把刚同步的最新官方代码合入 `custom/main`。

```bash
git switch custom/main
git pull --ff-only origin custom/main   # 先把远端 custom/main 拉下（团队协作场景）
git merge main                          # custom/main ← main（合并官方升级）
# 如果出现冲突 → 按 §2.9 冲突解决流程处理，合并后做一次 type-check
cd frontend && npm run type-check && npm run build && cd ..

git push origin custom/main
```

### 2.4 创建二开功能分支（P26 §4）

**目标**：从最新 custom/main 切临时分支开发，不直接改 custom/main。

```bash
# 新增功能
git switch -c feat/功能名称                # 例如 feat/videohub-batch2

# 修复问题
git switch -c fix/问题名称                 # 例如 fix/login-token-storage
```

### 2.5 修改并测试代码（P26-P27 §5）

**目标**：只在功能分支上改；范围验证通过后才允许 commit。

```bash
git status --short                        # 看清你改了哪些文件
git diff                                  # 逐行检查改动
git diff --check                          # 检查行尾空格/冲突标记残留

# --- 后端/通用测试（WeKnora 原生 Go make）---
make test                                 # 若 Makefile 提供

# --- 前端验证（二开主要改前端，必跑 3 项）---
cd frontend
npm run type-check                        # TypeScript 严格类型检查（0 error 才算过）
npm run build                             # Vite 生产构建成功才允许提 PR
# 手工验收：本批修改涉及的页面抽屉/弹窗/上传流程实际点击一遍
cd ..
```

### 2.6 提交二开代码（P27 §6）

**原则**：**少量多次 commit**；每个 commit **语义单一、可独立审查、可独立回滚**。严禁"一锅端 commit"（比如 docs+前端+skills 放在同一个 commit 里）。

```bash
# 1. 只选择本次 commit 要的文件（不要 git add .）
git add docs/xxx.md                       # 例：本次提交只含 docs
# git add frontend/src/views/videohub/    # 下一个 commit 再提交前端
# git add skills/preloaded/               # 再下一个 commit 再提交 skills

# 2. 暂存区检查（必须做，避免"多加了不该加的文件"上线事故）
git diff --cached --check                 # 空白/冲突残留
git diff --cached --stat                  # 改了多少文件、增删行数
git diff --cached                         # 逐行过一遍暂存区改动

# 3. commit：三段式规范
# 新增功能：
git commit -m "feat(scope): describe the feature"
# 修复问题：
git commit -m "fix(scope): describe the fix"
# 文档类（本项目单独 commit）：
git commit -m "docs(scope): describe"
```

**Commit message 三段式结构**（本次批 2 实际应用）：

```
docs: add WeKnora on-cloud deployment guide v0.7.2
      ↓     ↓
      │     └─ 主体描述（英文冒号+空格后开始；用中文写细节更易读）
      └─ 类型：feat / fix / docs / refactor / chore / test
             (scope) 可选，指明影响范围，例如 videohub / skills / upload
```

### 2.7 推送功能分支（P27 §7）

```bash
# 首次推送（设置 upstream，后续 git push 即可）
git push --set-upstream origin feat/功能名称

# 后续追加 commit 后的推送
git push
```

### 2.8 通过 PR 合入二开主线（P27-P28 §8）

| 项 | 值 |
|---|---|
| PR 来源分支 | `feat/功能名称` / `fix/问题名称` |
| **PR 目标分支** | **`custom/main`** |
| 仓库 | 自己的 Fork（例如 `lizi586586-code/vidsage`） |

> **⭐ 硬约束（PDF 5.1 P28）：不要把二开 PR 的目标设置为腾讯的官方 main。官方 main 只接受 upstream 同步。**

### 2.9 处理合并冲突（P29 §9）

```bash
# 发生冲突后，先看哪些文件冲突
git status
# 冲突标记：<<<<<<< HEAD  ...  =======  ...  >>>>>>> feat/x

# 1. 打开冲突文件 → 人工整合 → 保存
# 2. 对每一个解决的文件：
git add <已解决的文件>

# 3. 解决完所有冲突 → 检查空白 + 重跑测试
git diff --check
cd frontend && npm run type-check && npm run build && cd ..   # 前端改动必跑
make test                                                     # 后端改动必跑

# 4. 完成合并 commit + push
git commit
git push

# 想取消本次合并（冲突太乱，换个思路重写）：
git merge --abort
```

### 2.10 持续跟进官方更新（P29 §10）

**推荐频率**：每周一次，或官方发版后立即执行。流程 = 2.2 + 2.3：

```bash
git fetch upstream --prune
git switch main
git merge --ff-only upstream/main
git push origin main
git switch custom/main
git pull --ff-only origin custom/main
git merge main                      # 如果有冲突 → §2.9 解决 + 测试
git push origin custom/main
```

然后给尚未合并的 feature 分支同步最新 custom/main：

```bash
git switch feat/正在开发的分支
git merge custom/main               # 或 rebase（团队协作场景 merge 更安全）
```

### 2.11 确认后彻底删除备份（P29 §11）

```bash
git stash list                      # 查看所有备份 stash
git stash show stash@{0}            # 确认某个 stash 内容
git stash drop stash@{0}            # 单条删除
git stash clear                     # 全部清空（最后一个 feature 合入并部署后）
```

## 3. 5.2 把个性化代码提交到 GitHub（PDF 5.2）

开发完成 → PR → 合并 → 发布基线 ready，最终服务器部署只认 `custom/main`。流程图再强调一遍：

```
 upstream/main  ──ff──▶  origin/main  ──merge──▶  custom/main  ──▶  git switch -c feat/*
                                                                         │
                                                                         │ 开发 & 测试
                                                                         ▼
                                                                    3 commits 少量多次
                                                                         │
                                                                    git push -u origin feat/*
                                                                         │
                                                                     PR 审查 目标 custom/main
                                                                         │
                                                                squash/merge 合入 custom/main
                                                                         │
                                                            push origin custom/main 成功 ✓
```

### 3.1 本次批 2 实际提交示例（3 commits · 语义拆分）

```
5ed2e20b docs: add WeKnora on-cloud deployment guide v0.7.2      (1 file)
20588d88 feat(videohub): video list/detail/chat + upload modal + AI assistant (10 files)
18318868 feat(skills): 6 preloaded custom skills for transcript pipeline (28 files)
```

✅ 每个 commit 可独立审查、独立回滚。举例：如果 skills 上线后发现 Agent 召回异常 → 单独 `git revert 18318868` 即可，不会影响前端页面。

### 3.2 检查清单（每次 push feature 前必做）

- [ ] `git status` 干净；没有 untracked 临时文件、没有 `<<<<<<<` 冲突标记残留
- [ ] `git diff --check` 空白检查通过
- [ ] 前端：`npm run type-check` 0 error + `npm run build` 成功
- [ ] 本批修改涉及的交互（视频列表、上传弹窗、AI 助手全局/详情、Chat 页）**手工点过一遍**
- [ ] Commit message 三段式 + 语义拆分（docs / feat / fix 独立）
- [ ] `git log custom/main..HEAD --oneline` 清楚列出将要提交的 commit

### 4.2 两条构建路径对比

### 4.3 路径 A · 标准：Mac 构建 + 复用 §4 离线中转

**完整命令块（复制执行即可）**：

```bash
# ===== 本机 Mac =====
cd vidsage/frontend
TAG=wechatopenai/weknora-ui:v0.7.2-custom-$(date +%Y%m%d%H%M%S)

# 1. 前端生产构建 + Docker 镜像（linux/amd64）

npm run build                           # ← 产出 dist/

  -f frontend/Dockerfile \
  -t "$TAG" \

echo "镜像 Tag: $TAG"

# 2. 校验架构（必须 amd64 才能在腾讯云 CVM 跑）
docker image inspect "$TAG" --format '{{.Architecture}}'   # 期望输出：amd64

# 3. 离线导出 + 压缩（≈35MB，复用《上云步骤.md》§4.5-§4.7）

ls -lh "$TAR"

# 4. SCP 传输到服务器（复用 vidsage.pem）
scp -i ~/.ssh/vidsage.pem "$TAR" ubuntu@42.194.211.189:/tmp/
```

```bash
# ===== 服务器 Ubuntu =====
# 5. 导入镜像
sudo docker load -i /tmp/wechatopenai_weknora-ui_v0.7.2-custom-*.tar.gz
sudo docker images | grep weknora-ui   # 确认有新 tag

# 后续步骤统一走 §4.6 compose 切换（和路径 B 共用）
```

### 4.5 服务器代码同步（两条网络路径）

custom/main 合入并 push 后，服务器 /opt/vidsage 的 Git 库需要同步拉到同一个 commit。

**路径 A：GitHub 网络通畅（默认先试）**

```bash
cd /opt/vidsage
git rev-parse --abbrev-ref HEAD        # 期望：custom/main
git fetch origin custom/main --prune
git merge --ff-only origin/custom/main
git rev-parse --short HEAD              # 比对本地的 custom/main HEAD，应一致
```

**路径 B：腾讯云 → GitHub TLS 握手断连（降级路径，本次实战采用）**

project memory 已知问题：*GitHub TLS connection termination on Tencent Cloud requires Mac-local code packaging and SCP transfer*。两种等效做法：

```bash
# ===== 做法 1：git format-patch 3 个 patch（线性 commits 场景更直观）=====
# 本机 Mac：
cd vidsage
git format-patch -3 -o /tmp/vp-patches HEAD   # 本批有几个 patch 就写几
scp -i ~/.ssh/vidsage.pem /tmp/vp-patches/000*.patch ubuntu@42.194.211.189:/tmp/

# 服务器（先把 untracked 同名冲突文件移到 /tmp 备份，git am 会重新创建）：
cd /opt/vidsage
git am /tmp/0001-xxx.patch /tmp/0002-xxx.patch /tmp/0003-xxx.patch
git rev-parse --short HEAD              # （commit hash 会与本地不同，属 git am 正常重算）
```

```bash
# ===== 做法 2：git bundle 增量包（适合大量 commits / merge commit 非线性场景）=====
# 本机 Mac：
git bundle create /tmp/vidsage.bundle BASE_COMMIT..TIP_COMMIT
git bundle verify /tmp/vidsage.bundle
scp -i ~/.ssh/vidsage.pem /tmp/vidsage.bundle ubuntu@42.194.211.189:/tmp/

# 服务器：
cd /opt/vidsage
# 移走 untracked 同名冲突（同上）
git fetch /tmp/vidsage.bundle HEAD:refs/remotes/bundle/tip
git merge --ff-only refs/remotes/bundle/tip
```

> **注意**：git am / bundle fetch 会导致服务器的 commit hash 与本地 GitHub 不一致（因为 committer/时间戳被重算）。这是**正常行为**，只需要**内容、文件列表、父基线 commit 一致**即可追溯。

### 4.6 生产 Compose 切换 image tag + ⭐ 双文件启动硬约束

```bash
cd /opt/vidsage

# 1. 备份当前 compose override
cp docker-compose.cloud.yml \
   docker-compose.cloud.yml.bak-$(date +%Y%m%d%H%M%S)

# 2. 替换 frontend 镜像 tag（确保单引号包围 sed，$ 不被 shell 解析）
NEW_TAG='wechatopenai/weknora-ui:v0.7.2-custom-20260820154021'
sed -i "s|image: .*weknora-ui.*|image: ${NEW_TAG}|" docker-compose.cloud.yml

# 3. 校验 compose YAML 合法
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml config --quiet
# ✓ 无输出 = 合法；有输出就要修

# 4. ⭐⭐⭐ 双 compose 叠加启动（本次踩坑！禁止只用 cloud override 一个文件）
sudo docker compose \
  -f docker-compose.yml \
  -f docker-compose.cloud.yml \
  up -d frontend
```

**⭐ 为什么必须双文件？**（反例与原理）

`docker-compose.cloud.yml` 是"overlay override"，本身只定义 `services.frontend.image / deploy.resources / depends_on.condition`，**不包含 `ports / container_name / networks / 其它 4 个服务定义`**。如果只传 `-f docker-compose.cloud.yml`，会出现：

- ❌ frontend 与 app 不在同一个 network → **nginx upstream `app` 解析失败 → 公网 HTTP 502**
- ❌ 丢失 `container_name: WeKnora-frontend` → 与《上云步骤.md》§11.3 backup 脚本不匹配
- ❌ 丢失 `ports: - "80:80"` → **公网连不上 80 端口**
- ❌ depends_on 引用的 `app` 在单文件场景下不存在 → compose 报错

正确做法**永远传两个**：基础层 `docker-compose.yml` + 覆盖层 `docker-compose.cloud.yml`。

### 4.7 上线验收：⭐ 三联一致性（Git HEAD ↔ 镜像 Tag ↔ HTTP 200）

**每次个性化代码发布完毕，下面三项必须**全部匹配后才算上线完成。

#### [A] Git 侧（100% 追踪 + 正确分支）

```bash
cd /opt/vidsage
echo "Branch   : $(git rev-parse --abbrev-ref HEAD)"   # 期望：custom/main
echo "HEAD     : $(git rev-parse --short HEAD)"        # 期望：与 custom/main TIP 一致（或 git am 后内容一致）
# 关键文件追踪检查：
git ls-files frontend/src/components/videohub/AiAssistant.vue  # 期望：文件路径
git ls-files skills/preloaded/ | wc -l                       # 期望：≥28（6 skills 带 frontmatter）
git status --short                                             # 期望：只有 docker-compose* / backups 这类运维未跟踪
```

#### [B] Docker 侧（Compose 声明 == 容器实装）

```bash
# Compose 声明的 image：
grep -A1 '^  frontend:' docker-compose.cloud.yml
# 容器实装的 image：
sudo docker inspect WeKnora-frontend --format '{{.Config.Image}}'
# 两者必须同一个 tag！

# 健康状态 & 端口：
sudo docker ps --filter name=WeKnora --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
# 期望：frontend Up + 端口 0.0.0.0:80->80/tcp；app/docreader/postgres/redis 均 Up/healthy
```

#### [C] HTTP 侧（本机 + 公网 + 资源 hash）

```bash
# 1. 本机前端入口：
curl -sS -o /dev/null -w "本机 frontend /: %{http_code}\n" http://127.0.0.1:80/
# 2. 本机 app 健康：
curl -sS -o /dev/null -w "本机 app /health : %{http_code}\n" http://127.0.0.1:8080/health
# 3. 公网入口（从自己的 Mac 或手机 4G 打）：
curl -sS -o /dev/null -w "公网 http://42.194.211.189/ : %{http_code}  size=%{size_download}B  time=%{time_total}s\n" \
  -L --max-time 20 http://42.194.211.189/
# 4. 内容 hash 匹配：验证 index.html 引用的 main-XXXX.js 与本地 npm run build 产物一致
curl -sSL --max-time 20 http://42.194.211.189/ | grep -oE 'main-[A-Za-z0-9]+\.js' | head -1
# 期望：同本地 dist/assets/main-*.js hash（证明不是旧缓存）
```

✅ **三联全部通过才算发布完成**。三联中任何一项不通过（例如 Git untracked 大量源码、容器 tag 对不上、公网 HTTP 502）**必须先回滚**，不允许在生产环境"边 debug 边修"。

## 5. 个性化版本的升级 / 回滚

### 5.1 升级（custom tag N → N+1）

流程 = §4 全流程：
1. 本地 feature 开发 → PR → 合入 custom/main → 推送到 GitHub
2. 打新的 custom tag（`v0.7.2-custom-新时间戳`）→ Mac 构建 → 离线中转 → load
3. compose 备份 + sed 切 image → 双文件 `up -d frontend`
4. 三联验收 → 附录登记

### 5.2 回滚（custom tag N → N-1，紧急预案）

出现以下任一情况**立即回滚**：三联不通过 / 核心页面打不开 / 登录失败 / 上传报错 / 5xx。

```bash
cd /opt/vidsage

# 1. 确认上一个 tag 仍在本地镜像缓存（§5.1 升级后严禁 docker rmi 旧版本，至少保留 1 个可回滚版本）
sudo docker images | grep weknora-ui

# 2. compose restore（每次升级都会有 xxx.bak-YYYYMMDDHHMMSS 备份）
ls docker-compose.cloud.yml.bak-*
cp docker-compose.cloud.yml.bak-<上一版本时间戳>  docker-compose.cloud.yml

# 3. 校验 + 重启 frontend
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml config --quiet
sudo docker compose -f docker-compose.yml -f docker-compose.cloud.yml up -d frontend

# 4. 立即三联验收（§4.7），确认回滚成功
```

## 6. 官方 WeKnora 版本升级与 custom/main 衔接（Rebase 流程）

假设官方发布 `v0.7.3`。正确顺序：

1. **先冻结 feature 分支开发**，先把 custom/main 的代码干净同步
2. §2.2 同步 `upstream/main → origin/main`（v0.7.2 → v0.7.3）
3. §2.3 把 `origin/main → custom/main`（注意这里很可能有冲突，因为我们改了 frontend/skills 等 39 个文件；必须逐条人工解决+完整测试）
4. 本地构建新的 custom 镜像：`wechatopenai/weknora-ui:v0.7.3-custom-YYYYMMDDHHMMSS`（基线版本号改为 v0.7.3）
5. 完整本地手工验收 + 类型检查 + build
6. §4 部署到生产：离线中转 → compose 切换 → 三联验收
7. **最后**才同步各个 `feat/*` 开发分支：`git switch feat/x && git merge custom/main`

> **安全原则**：官方升级与新功能开发**永远不要混合在同一个 PR**。先升级基线稳定跑一周，再开新的 feat 分支。

## 7. 安全红线与禁止事项

1. ⛔ **代码仓库**：`.env` / AccessKey / AppKey / 任何密码**严禁 commit**。所有密钥走环境变量或 `.env`（`chmod 600`，gitignore 中已排除）。
2. ⛔ **Git 分支**：二开 PR 的目标**绝对不能是腾讯 upstream/main**。只能 PR 到自己的 `custom/main`。
3. ⛔ **服务器构建**：2 vCPU / 4GB **禁止源码 build Docker 镜像**。
4. ⛔ **启动命令**：`docker compose up -d` **禁止单传 docker-compose.cloud.yml**；永远 `-f docker-compose.yml -f docker-compose.cloud.yml` 双文件叠加。
5. ⛔ **镜像架构**：Apple Silicon Mac 构建镜像**必须显式 `--platform linux/amd64`**，否则云服务器无法启动容器。
6. ⛔ **服务器网络**：Git 不允许设置 7897 等 HTTP 代理（会直接 connection refused）。GitHub 不通走 §4.5-B 的 format-patch / bundle 降级。
7. ⛔ **生产镜像清理**：至少保留 1 个上一版 custom tag 镜像在服务器本地缓存，保证 5 分钟内可回滚。
8. ⛔ **没有三联验收不算完成**。
