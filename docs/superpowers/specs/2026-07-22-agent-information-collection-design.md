# 智能体动态信息采集与系统管理员数据中心设计

## 1. 背景

当前结构化提问由模型自主决定是否调用 `ask_user`。即使 Skill 要求补充信息，模型仍可能直接输出普通文本问题，导致采集流程不稳定，也无法形成可查询、可更新、可审计的用户档案。

本设计将信息采集从 Skill 提示词提升为智能体的确定性运行能力。系统管理员在智能体中配置采集目标和字段，后端在 Agent 推理前检查用户档案，按实际缺失字段逐题采集，并在后续对话中静默更新最新值。只有系统管理员能查看全局档案、历史和导出数据。

## 2. 目标

- 系统管理员可为每个智能体配置独立的信息采集目标和字段 Schema。
- 用户首次使用智能体时，系统强制采集当前缺失的必填字段。
- 题目数量根据字段配置、用户已有值和条件规则动态计算，不设固定上限为三题。
- 采集过程中显示已完成项和剩余问题数，支持刷新、断线和跨页面恢复。
- 后续会话不向用户展示档案摘要，也不重复询问已有有效值。
- 用户在自然语言中明确提供新值时，系统自动更新最新档案。
- 每次字段变更保留旧值、新值、来源、置信度、消息和操作人。
- 系统管理员可跨租户查询、修正、审计并导出 CSV/XLSX。

## 3. 非目标

- 租户管理员和普通用户不具备档案查询权限。
- 模型不能创建配置之外的新档案字段。
- 第一版不提供完整规则引擎，只支持单条件字段联动。
- 第一版不允许用户查看或编辑自己的档案摘要。
- 第一版不把采集模板抽象为可跨智能体复用的独立资源。

## 4. 核心原则

1. **确定性优先**：是否开始采集由后端字段检查决定，不依赖模型选择工具。
2. **Schema 约束**：只有系统管理员配置的字段才能写入档案。
3. **逐题持久化**：每道题提交后立即保存，避免长流程中断丢失。
4. **静默复用**：已有有效值不向用户展示，也不重复询问。
5. **可追溯更新**：覆盖最新值前必须写入字段级历史。
6. **最小权限**：档案读取、修改、导出仅向系统管理员开放。

## 5. 总体架构

系统由四个边界清晰的模块组成：

### 5.1 采集配置

采集配置属于 `CustomAgentConfig`，随智能体创建和更新接口读写。配置包含：

- 是否启用采集
- 采集目标说明
- Schema 版本
- 字段定义列表
- 自然语言抽取开关和置信度阈值

### 5.2 确定性采集协调器

在 Agent Engine 启动前执行：

1. 加载智能体采集配置。
2. 加载当前“租户 + 智能体 + 用户”的最新档案。
3. 评估字段显示条件。
4. 计算缺失且需要采集的字段。
5. 若存在缺失字段，发送结构化 SSE 事件并等待回答。
6. 逐题保存答案并重新计算剩余字段。
7. 必填字段完成后恢复原 Agent 请求。

### 5.3 用户档案与历史

最新档案用于快速读取和导出；字段历史用于追溯。两者在同一事务中更新，避免最新值和历史不一致。

### 5.4 系统管理员数据中心

提供跨租户列表、详情、字段修正、历史查看和导出。所有读取详情、修改和导出动作写入系统审计日志。

## 6. 智能体采集配置

### 6.1 配置结构

```json
{
  "collection_enabled": true,
  "collection_goal": "收集劳动争议初步评估所需事实",
  "collection_schema_version": 3,
  "collection_extract_from_messages": true,
  "collection_extraction_threshold": 0.85,
  "collection_collect_optional_during_intake": false,
  "collection_fields": [
    {
      "key": "dismissal_notice_method",
      "label": "公司以什么方式通知辞退？",
      "description": "用于判断解除程序和举证方向",
      "type": "single_choice",
      "required": true,
      "enabled": true,
      "order": 10,
      "options": [
        {"id": "written_with_reason", "label": "书面通知且说明理由"},
        {"id": "written_without_reason", "label": "书面通知但未说明理由"},
        {"id": "oral", "label": "口头通知"},
        {"id": "no_formal_notice", "label": "无正式通知"}
      ],
      "validation": {},
      "visible_when": null
    }
  ]
}
```

### 6.2 字段类型

- `single_choice`
- `multiple_choice`
- `short_text`
- `long_text`
- `number`
- `date`

### 6.3 通用字段属性

- `key`：智能体内稳定且唯一的 ASCII 字段键，发布后不可直接修改。
- `label`：面向用户的问题文本。
- `description`：面向管理员的用途说明，也用于自然语言抽取。
- `required`：是否必须采集后才能恢复 Agent。
- `enabled`：是否参与当前 Schema。
- `order`：采集顺序。
- `options`：单选和多选的选项。
- `validation`：文本长度、数字范围、日期范围等约束。
- `visible_when`：简单条件显示规则。

### 6.4 条件规则

第一版只支持引用一个前置字段：

```json
{
  "field": "employment_status",
  "operator": "equals",
  "value": "dismissed"
}
```

支持操作符：

- `equals`
- `not_equals`
- `contains`
- `not_empty`
- `empty`

被引用字段必须排在当前字段之前。保存配置时检测不存在的引用、自引用和循环依赖。

### 6.5 Schema 发布规则

- 新建字段、修改必填状态、类型、选项或显示条件时递增 Schema 版本。
- 仅修改标签、描述或排序也递增版本，以确保运行时和审计记录可定位到准确配置。
- 删除已发布字段采用停用，不物理删除历史数据。
- 字段类型发布后不可原地更换；管理员需停用旧字段并新建字段。

## 7. 动态题目计算

待采集字段定义为：

```text
已启用字段
∩ 当前条件可见字段
∩ 当前没有有效值的字段
```

每次提交答案后重新计算条件和剩余字段，因此后续题目可动态增加或减少。

进度不使用固定的 `第 N / 总数` 作为唯一表达，改为：

- `已完成 N 项`
- `剩余 M 个问题`

内部事件仍携带当前顺序和动态总量，便于兼容现有组件；前端以剩余数为主要展示。当条件答案解锁新字段时，剩余数可增加。

可选字段不阻塞 Agent。系统在必填字段完成后停止采集；是否主动询问可选字段由智能体级配置 `collection_collect_optional_during_intake` 控制，默认关闭。

## 8. 采集流程与恢复

### 8.1 首次采集

```text
接收用户消息
  -> 解析智能体
  -> 从本轮用户消息抽取已明确提供的配置字段
  -> 校验并更新档案与历史
  -> 加载采集 Schema 与最新档案
  -> 计算缺失字段
  -> 发送 collection_input_required SSE
  -> 等待并验证答案
  -> 保存档案与历史
  -> 重算剩余字段
  -> 全部必填完成
  -> 启动原 Agent 请求
```

### 8.2 中断恢复

- 当前待回答字段写入 Redis，沿用现有用户输入 Gate 的超时和所有权校验。
- 已完成答案已经写入 PostgreSQL，不依赖单次 SSE 连接。
- 页面刷新后通过待处理输入接口恢复当前问题。
- SSE 断开后继续流时，不重复创建同一字段的问题。
- 同一用户同时在多个页面回答时，只有第一个合法提交成功，其余返回已处理状态。

### 8.3 Schema 变化

- 用户已有档案按字段键复用，不要求整份重采。
- 新增必填字段在用户下次使用时补采。
- 字段变为不可见时，最新值保留但标记为 inactive，不参与缺失检查和默认导出。
- 字段重新启用后，原值若仍通过校验则继续复用。

## 9. 自然语言静默更新

### 9.1 抽取时机

每轮用户消息持久化后、缺失字段检查前执行一次受 Schema 约束的抽取。这样用户已在当前消息中明确提供的信息会先写入档案，不会被结构化流程重复询问。抽取调用设置独立短超时；超时或失败时记录诊断信息并继续缺失检查，不阻塞聊天主流程。

### 9.2 抽取约束

模型接收当前智能体的字段 Schema，只能返回配置字段键：

```json
{
  "updates": [
    {
      "field_key": "employment_years",
      "value": 3,
      "confidence": 0.96,
      "evidence": "我在公司工作三年了"
    }
  ]
}
```

- 未配置字段一律丢弃。
- 低于智能体阈值的结果不写入。
- 模糊、推测、否定上下文或第三方信息不覆盖已有值。
- 写入前使用同一字段验证器校验类型和范围。
- 新值与现值相同则不新增历史。
- 明确的新值覆盖现值，并记录 `message_extraction` 来源。

### 9.3 并发控制

档案更新使用乐观锁版本号。并发冲突时重新读取最新档案并按消息时间重放，较新的明确值胜出。

## 10. 数据模型

### 10.1 `agent_collection_profiles`

建议字段：

- `id` UUID 主键
- `tenant_id` BIGINT
- `agent_id` VARCHAR
- `user_id` VARCHAR
- `schema_version` INTEGER
- `values` JSONB
- `inactive_values` JSONB
- `required_total` INTEGER
- `required_completed` INTEGER
- `is_complete` BOOLEAN
- `lock_version` INTEGER
- `created_at` / `updated_at` / `deleted_at`

唯一索引：`tenant_id, agent_id, user_id`，排除软删除记录。

`values` 中每个字段保存值、更新时间、来源和最后消息 ID，但不嵌入完整历史。

### 10.2 `agent_collection_history`

建议字段：

- `id` UUID 主键
- `profile_id` UUID
- `tenant_id` BIGINT
- `agent_id` VARCHAR
- `user_id` VARCHAR
- `field_key` VARCHAR
- `schema_version` INTEGER
- `old_value` JSONB
- `new_value` JSONB
- `source` VARCHAR
- `confidence` NUMERIC，可为空
- `source_message_id` VARCHAR，可为空
- `actor_user_id` VARCHAR，可为空
- `created_at`

索引覆盖 `profile_id + created_at`、`tenant_id + agent_id`、`user_id` 和 `field_key`。

## 11. API 设计

### 11.1 智能体配置

沿用现有智能体创建、更新和详情接口，在 `config` 中增加采集配置。服务层负责规范化和验证。

### 11.2 用户回答

扩展现有用户输入提交接口，使其支持六种字段类型。请求包含：

- `pending_id`
- `field_key`
- `schema_version`
- `value`

服务端从待处理记录读取可信 Schema，不接受客户端自行声明字段规则。

### 11.3 系统管理员接口

- `GET /api/v1/system/admin/collection-profiles`
- `GET /api/v1/system/admin/collection-profiles/:id`
- `GET /api/v1/system/admin/collection-profiles/:id/history`
- `PUT /api/v1/system/admin/collection-profiles/:id/fields/:field_key`
- `POST /api/v1/system/admin/collection-profiles/export`
- `GET /api/v1/system/admin/collection-exports/:id`

列表支持租户、智能体、用户、完整状态、字段值和更新时间筛选。导出任务保存筛选快照，并输出 CSV 和 XLSX。

## 12. 权限、隐私与审计

- 读取档案、历史和导出接口只允许 `system_admin`。
- 普通用户只可向自己的待处理问题提交答案。
- 租户管理员没有档案读取权限。
- 系统管理员的详情查看、字段修改、导出创建和文件下载均写入系统审计日志。
- 禁止配置密码、验证码、访问令牌、API Key、私钥等字段；字段键、标签和描述都参与敏感词校验。
- API 和日志不得输出模型密钥、认证信息或未经请求的完整档案内容。
- 用户或智能体删除后默认软删除档案；合规清除由系统管理员显式执行并记录审计。

## 13. 前端设计

### 13.1 智能体编辑器

在现有智能体编辑器增加“信息采集”页签：

- 启用开关和采集目标
- 自然语言更新开关和置信度阈值
- 字段列表、新增、复制、排序、停用
- 字段属性编辑
- 简单条件配置
- 实时问题卡片预览
- 发布前校验摘要

### 13.2 用户问题卡片

复用现有聊天流卡片并扩展字段类型：

- 单选使用 Radio
- 多选使用 Checkbox
- 短文本和长文本使用对应输入框
- 数字使用带范围校验的数字输入
- 日期使用日期选择器
- 顶部显示已完成项和剩余问题数
- 保存中、失败重试、已提交和恢复状态明确

### 13.3 系统管理员数据中心

新增“采集数据”页面：

- 汇总：用户数、档案数、今日更新数、待补全数
- 筛选：租户、智能体、用户、完整状态、更新时间、字段值
- 列表：用户、租户、智能体、完整度、最后更新时间
- 详情抽屉：最新字段摘要和字段级历史
- 字段修正：必须填写修改原因
- 导出：当前筛选结果，支持 CSV/XLSX

## 14. 错误处理

- 单题保存失败：停留当前题，保留用户输入并允许重试。
- 条件计算失败：记录错误并仅采集无条件必填字段，不启动不确定字段。
- 自然语言抽取失败：记录诊断信息，不影响聊天。
- 导出失败：任务标记失败并向管理员展示可操作错误，不生成残缺文件。
- Schema 冲突：拒绝保存智能体配置并指出具体字段和依赖。
- 档案并发冲突：服务端重试有限次数，仍失败则记录任务并保持旧值。

## 15. 测试与验收

### 15.1 后端

- 字段配置校验、条件循环检测和 Schema 版本递增。
- 首次使用按缺失字段开始采集。
- 已有有效值不重复提问。
- 六种字段类型的解析与校验。
- 条件联动后动态增减剩余字段。
- 每题提交后档案和历史原子更新。
- SSE 中断、刷新和重复提交恢复。
- 全部必填字段完成后恢复原 Agent。
- 自然语言明确更新成功写入，低置信度不覆盖。
- 普通用户和租户管理员无法读取档案。
- 系统管理员跨租户查询、修改和导出。
- 审计日志覆盖详情查看、修改、导出和下载。

### 15.2 前端

- 六种字段组件及校验错误。
- 动态剩余数展示。
- 条件字段出现和隐藏。
- 刷新后的当前问题恢复。
- 重复提交和保存失败状态。
- Admin 筛选、详情、历史、修改和导出流程。
- 桌面和移动视口无文字溢出、遮挡和布局跳动。

### 15.3 端到端验收

1. 系统管理员创建智能体并配置带条件的采集字段。
2. 新用户首次发消息，系统在 Agent 回答前显示第一道缺失字段。
3. 回答触发条件后，剩余问题数动态变化。
4. 完成必填字段后，Agent 自动继续原问题。
5. 新会话不重复采集已有字段，也不展示摘要。
6. 用户自然语言明确修改某字段，Admin 看到最新值和历史旧值。
7. Admin 跨租户筛选并导出 CSV/XLSX，导出内容与筛选结果一致。
8. 非系统管理员访问任何档案读取接口均被拒绝。

## 16. 交付拆分

建议按以下顺序实施：

1. 字段 Schema、配置校验和智能体编辑器。
2. 档案与历史表、Repository 和 Service。
3. 确定性采集协调器及六种问题组件。
4. 中断恢复和 Agent 自动继续。
5. 自然语言静默更新。
6. 系统管理员数据中心、审计和导出。
7. 全量回归、移动端验证和部署迁移。
