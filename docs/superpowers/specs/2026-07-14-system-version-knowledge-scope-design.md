# WeKnora 系统隔离与业务版本知识范围设计

> 状态：已批准设计
> 日期：2026-07-14
> 首期范围：A1，单系统端到端试点并支持多系统联合查询

## 1. 背景

WeKnora 当前可以为不同系统创建独立知识库，也可以在问答时同时选择多个知识库。这一能力适合作为系统隔离的基础，但现有知识标签不足以承担确定性的业务版本隔离：标签主要面向文档分类，多标签筛选为 OR 语义，内置知识图谱工具也没有统一的版本范围参数。

本设计将 WeKnora 作为知识图谱主平台进行二次开发，采用“每系统一个知识库 + 结构化知识范围”的方案。知识库负责系统隔离，结构化范围负责业务版本隔离，标签继续用于分类和辅助筛选。

## 2. 目标

首期实现以下能力：

1. 每个业务系统由一个 WeKnora 知识库承载，查询单个系统时不得命中其他系统数据。
2. 一个系统可以维护多个业务版本，每个版本可以涉及多个项目。
3. 系统知识分为系统公共知识和版本专属知识。
4. `project_id` 仅用于可选筛选和来源追溯，不参与强制隔离。
5. 一个租户配置一个默认部门公共知识库，系统问答时自动加入该知识库。
6. 多系统联合查询时，每个系统默认使用各自的当前运行版本，也可以分别选择历史版本。
7. 文档检索、Agent 工具和 Neo4j 查询使用同一个后端解析范围。
8. 所有结果保留部门、系统、版本、项目和原始文档来源，支持后续风险关联分析与报告生成。
9. 二次开发代码保持模块化和向后兼容，以便持续合并腾讯 WeKnora 上游更新。

## 3. 非目标

首期不实现以下内容：

1. 不按用户或角色限制可访问系统；当前租户内所有用户可访问全部系统。
2. 不强调或预定义具体测试类型。
3. 不把 `project_id` 建模为独立项目主数据，也不实施项目级强隔离。
4. 不实现类似 Git 的文档修订版本控制；版本仅指业务系统发布版本。
5. 不自动创建跨系统 Neo4j 关系；跨系统分析先分别检索各系统证据，再由 Agent 关联和比较。
6. 不在 A1 中建设统一风险事实表、完整安全风险分析工具或 Word 模板渲染器。
7. 不依赖标签、提示词或大模型判断来保证系统和版本隔离。

## 4. 关键决策

### 4.1 系统与知识库一一对应

一个系统知识库是一个稳定的系统数据容器。知识库名称可以修改，但 `system_id` 是稳定标识，不能由名称推导。

部门公共知识存放在独立知识库中，不复制到各系统知识库。系统查询自动组合：

```text
默认部门公共知识库
+ 系统公共知识
+ 该系统选定业务版本知识
```

多系统查询对每个系统独立解析版本后，再合并证据。

### 4.2 结构化范围承担隔离

文档范围只有三种合法类型：

- `department_public`：部门公共知识。
- `system_common`：某系统所有版本共享的知识。
- `system_version`：某系统指定业务版本的专属知识。

标签与 `project_id` 只能缩小结构化范围，不能扩大结构化范围。

### 4.3 后端生成不可变查询范围

客户端提交知识库和版本选择，后端根据知识库映射解析 `system_id`，验证版本归属并生成 `ResolvedScope`。Agent 和大模型不能输入、删除或修改 `system_id`、`version_id` 及部门公共库范围。

### 4.4 版本状态不控制可写性

业务版本可以标记状态和当前运行版本，但状态不冻结版本。一个版本可以持续接收多个项目的材料。一个系统最多存在一个 `is_current=true` 的版本。

## 5. 模块与 seam

### 5.1 Scope Catalog Module

责任：

- 管理知识库的部门公共或系统容器声明。
- 管理 `system_id` 与知识库映射。
- 管理业务版本、状态和当前运行版本。
- 保存每份文档的结构化范围。

接口只暴露容器、版本和文档范围的创建、查询及校验操作，不负责检索或图谱实现。

### 5.2 Scope Resolver Module

这是系统唯一的范围控制 seam。其最小接口为：

```go
ResolveWriteScope(ctx, knowledgeBaseID, selection) (ResolvedWriteScope, error)
ResolveQueryScope(ctx, selection) (ResolvedQueryScope, error)
```

`ResolveWriteScope` 校验上传范围并返回可信写入上下文。`ResolveQueryScope` 自动加入部门公共知识库，并为每个系统解析公共知识、指定版本知识和可选项目筛选。

调用者不需要理解标签关系、文档 ID 解析或 Neo4j 条件。删除该模块后，这些复杂性会重新散落到上传、聊天、Agent 和图谱代码中，因此该模块应保持为深模块。

### 5.3 Ingestion Adapter

在现有知识上传和异步解析 seam 接入：

- 创建文档前调用 `ResolveWriteScope`。
- 在同一数据库事务中创建 `knowledge` 和 `knowledge_scope`。
- 异步任务只携带 `knowledge_id`，Worker 从数据库重新读取可信范围。
- 分块、向量索引和图谱抽取继承文档范围，不允许独立选择范围。

### 5.4 Retrieval Adapter

在现有聊天检索和 Agent 检索 seam 接入：

- 新请求使用结构化系统版本选择生成 `ResolvedQueryScope`。
- A1 可以复用现有按 `knowledge_ids` 限定文档的检索路径，避免同时改写所有检索存储 Adapter。
- 用户标签和 `project_id` 先解析文档集合，再与结构化范围取交集。
- 结果必须附带系统、版本、项目和范围类型。

### 5.5 Graph Adapter

Neo4j 节点和关系增加以下范围属性：

- `tenant_id`
- `knowledge_base_id`
- `knowledge_id`
- `scope_type`
- `system_id`
- `version_id`
- `project_id`

现有知识库/文档命名空间继续用于兼容删除和追踪，但查询隔离以结构化范围属性为准。图谱查询失败时不得退回无范围查询。

### 5.6 Scoped Agent Tools

Agent 工具注册时绑定 `ResolvedQueryScope`：

```text
ScopedGraphTool(resolvedScope).query(query)
ScopedKnowledgeSearch(resolvedScope).search(query)
```

大模型只提供查询内容，不提供系统或版本参数。这样可以避免模型填错、漏填或主动扩大范围。

## 6. 数据模型

### 6.1 `scope_containers`

| 字段 | 说明 |
|---|---|
| `knowledge_base_id` | 主键，同时外键关联 `knowledge_bases.id` |
| `tenant_id` | 所属租户；用于数据库级租户唯一约束和查询校验 |
| `container_type` | `department_public` 或 `system` |
| `system_id` | 系统容器必填，部门公共容器为空 |
| `is_default_department` | 是否为租户默认部门公共知识库 |
| `created_at` / `updated_at` | 审计时间 |

约束：

- 同一租户最多一个默认部门公共知识库，使用 `tenant_id` 条件唯一索引保证。
- 同一租户内 `system_id` 唯一，使用 `(tenant_id, system_id)` 唯一约束保证。
- `tenant_id` 必须与关联知识库的租户一致。
- 普通旧知识库可以没有 `scope_containers` 记录，并继续使用原有行为。

### 6.2 `system_versions`

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `tenant_id` | 所属租户；参与系统归属和组合外键校验 |
| `system_id` | 所属系统 |
| `version_key` | 系统内稳定版本标识 |
| `display_name` | 显示名称 |
| `status` | `active`、`maintenance` 或 `retired` |
| `is_current` | 是否为当前运行版本 |
| `created_at` / `updated_at` | 审计时间 |

约束：

- 同一租户的同一系统内 `version_key` 唯一。
- 同一租户的同一系统最多一个当前运行版本。
- `(tenant_id, system_id)` 必须引用同租户的系统容器。
- 状态不限制写入。
- 被文档引用的版本不能物理删除，只能修改状态。

### 6.3 `knowledge_scopes`

| 字段 | 说明 |
|---|---|
| `knowledge_id` | 主键，同时外键关联文档 |
| `tenant_id` | 所属租户；用于读取时 fail-closed 校验和图谱属性继承 |
| `scope_type` | 三种合法范围之一 |
| `system_id` | 系统公共和系统版本范围必填 |
| `version_id` | 系统版本范围必填 |
| `project_id` | 系统版本范围下可选 |
| `created_at` / `updated_at` | 审计时间 |

约束：

- `department_public` 的系统、版本和项目字段必须为空。
- `system_common` 必须有系统，版本和项目为空。
- `system_version` 必须有系统和属于该系统的版本，项目可选。
- `tenant_id` 必须与文档、系统容器和版本的租户一致。
- 每份文档只有一个结构化范围。

### 6.4 标签保持独立

现有 `knowledge_tag_relations` 不变，继续支持文档类型、材料类型、测试分册和用户分类。标签不决定结构化范围，也不能放宽结构化范围。

## 7. 写入数据流

1. 用户在系统知识库上传文档并选择系统公共或版本专属范围；版本专属范围可填写 `project_id`。
2. Handler 调用 `ResolveWriteScope`。
3. Scope Resolver 从知识库映射解析 `system_id`，验证版本属于该系统并验证字段组合。
4. `knowledge` 与 `knowledge_scope` 在同一事务中创建。
5. 异步任务只传 `knowledge_id`。
6. Worker 从数据库加载范围后执行解析、分块、索引和图谱抽取。
7. 任何阶段读取不到有效范围时任务失败，不得作为无范围文档继续处理。

文档开始解析后，A1 不允许直接把它移动到另一版本。范围填错时删除后重新上传。带原子重建索引和审计记录的范围迁移能力作为后续变更。

## 8. 查询数据流

请求表达每个选中系统的版本：

```json
{
  "system_scopes": [
    {
      "knowledge_base_id": "kb-system-a",
      "version_id": "version-a-2",
      "project_id": null
    },
    {
      "knowledge_base_id": "kb-system-b",
      "version_id": "version-b-3",
      "project_id": "project-x"
    }
  ]
}
```

处理流程：

1. 未显式指定版本时，解析该系统当前运行版本。
2. 自动加入默认部门公共知识库。
3. 每个系统解析为“系统公共 + 指定版本”，并应用可选项目和标签交集。
4. 文档检索和图谱查询使用同一个 `ResolvedQueryScope`。
5. 各系统结果分别保留来源，再执行排序、去重和 Agent 汇总。

首期跨系统关联分析只合并证据和子图结果，不自动创建跨系统 Neo4j 边。

## 9. 页面与请求兼容

### 9.1 知识库管理

- 知识库设置增加“部门公共知识库”或“系统知识库”声明。
- 系统知识库增加业务版本管理入口。
- 上传对话框增加“系统公共/版本专属”选择、版本选择和可选项目编号。

### 9.2 问答入口

- 保留现有多知识库选择体验。
- 每个系统知识库显示版本选择，默认当前运行版本。
- 部门公共知识库由后端自动加入，不允许客户端取消。
- 回答引用显示系统、版本、项目和文档来源。

### 9.3 向后兼容

- 新范围字段为可选请求扩展。
- 未登记为范围容器的旧知识库继续走现有逻辑。
- `ENABLE_KNOWLEDGE_SCOPE=false` 时关闭新范围行为。

## 10. 失败处理

- 上传未选择合法范围：拒绝创建。
- 版本不属于目标系统：返回请求错误。
- 系统没有当前版本且请求未指定版本：返回范围无法解析错误，提示用户选择版本。
- 默认部门公共知识库未配置：范围查询返回配置错误，不静默忽略。
- 异步任务读取不到范围：任务失败，不创建无范围索引。
- Neo4j 无法应用范围：图谱查询失败，不降级为全库查询。
- 普通问答部分系统失败：允许返回其他系统结果，但明确标记结果不完整。
- 正式报告任一目标系统失败：整份报告失败，不生成部分报告。

## 11. 存量迁移

迁移采用显式、可预览流程：

1. 创建三张新增表和约束。
2. 配置默认部门公共知识库。
3. 将现有知识库登记为系统知识库并分配稳定 `system_id`。
4. 创建已有业务版本。
5. 预览文档到结构化范围的映射。
6. 人工确认后批量写入 `knowledge_scopes`。
7. 重新抽取现有图谱或补写可验证的范围属性。
8. 通过隔离测试后开启范围查询。

不得直接依据现有标签自动提交迁移结果。标签可以辅助预览，但必须人工确认。

## 12. 回滚

- 使用 `ENABLE_KNOWLEDGE_SCOPE` 控制新能力。
- 新表和 Neo4j 属性均为增量数据。
- 数据库迁移不直接改写存量文档。
- 关闭功能开关后，旧知识库恢复现有检索行为。
- 试点失败时保留范围数据用于排查，无需回滚全部知识库。

## 13. 多风险分析与 Word 报告扩展

当前范围底座可以支撑后续多个安全风险类型的关联分析，但后续需要两个独立变更。

### 13.1 统一风险分析模块

结构化风险事实库保存风险类型、严重度、状态、资产、规则、时间和来源；Neo4j 保存影响、定位、依赖、复现、同源和整改关系；RAG 提供原始报告、规范和整改证据。

安全风险分析 Agent 使用绑定范围的受控工具：

- `risk_query`
- `risk_stats`
- `risk_compare`
- `risk_trace`
- `evidence_search`

Agent 不直接执行任意 SQL 或 Cypher。

### 13.2 Word 模板报告模块

报告模块负责模板注册、模板版本、章节/表格/图表占位映射、报告载荷校验和 DOCX 渲染。大模型只撰写分析文字，指标、排名、趋势、表格和图表数据必须由受控工具产生。

现有内置数据分析师继续用于 CSV/XLSX 临时分析，不作为正式多风险分析事实源。

## 14. 验收与 Murphy 测试

### 14.1 核心成功场景

1. 系统 A 查询不会命中系统 B 文档或图谱节点。
2. 系统 A v2.0 查询只包含部门公共、系统 A 公共和系统 A v2.0 知识。
3. 系统 A v1.0 与系统 B v3.0 可以联合查询，每条证据来源明确。
4. 部门公共知识库始终参与范围问答。
5. `project_id` 和标签能够缩小结果，但不能扩大系统或版本范围。
6. 文档检索与图谱查询保持相同边界。

### 14.2 对抗与异常场景

1. 伪造其他系统的 `version_id` 被拒绝。
2. Agent 尝试更改范围无效。
3. 标签 OR 组合不能绕过结构化范围。
4. 两个请求并发设置当前版本时，数据库最多保留一个当前版本。
5. 被引用版本不能物理删除。
6. Worker 丢失范围、向量存储失败或 Neo4j 失败时不产生无范围数据。
7. 部分系统失败时，普通问答明确提示不完整；正式报告不输出。
8. 老知识库在关闭功能开关或未登记容器时保持原行为。

### 14.3 验证层级

- Scope Resolver 单元测试。
- Repository 唯一约束、引用约束和事务测试。
- Handler 输入组合与错误码测试。
- 上传到异步处理的集成测试。
- 文档检索和 Neo4j 范围一致性测试。
- 多系统、多版本和并发测试。
- 前端版本选择与来源展示测试。
- Docker Compose 冒烟测试。

## 15. Fork 与上游同步策略

当前本地仓库的 `origin` 仍指向腾讯仓库。正式实施前必须调整为：

```text
origin   -> 用户的 GitHub Fork
upstream -> https://github.com/Tencent/WeKnora.git
```

分支策略：

- `origin/main`：用户 Fork 的稳定集成分支。
- `codex/knowledge-scope-foundation`：本次 A1 功能分支。
- `codex/sync-upstream-YYYYMMDD`：定期合并上游的同步分支。

已共享主分支不强制 rebase。同步上游时先创建同步分支，合并 `upstream/main`，解决冲突并完成后端、前端、迁移、Docker 和隔离测试后再合入用户 `main`。

为降低冲突，本次开发必须：

- 将范围逻辑集中在 Scope Module。
- 使用增量表、可选请求字段和功能开关。
- 前端新增独立版本选择模块。
- 只在上传、检索、Agent 和图谱的稳定 seam 接入。
- 不进行与目标无关的大规模重构。
