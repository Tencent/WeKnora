# 全租户访问账号管理设计

## 背景

当前 `users.can_access_all_tenants` 只能通过直接修改数据库维护。系统设置页已经支持维护 `is_system_admin`，但两项权限的授权边界不同，本期不改变现有系统管理员授予与撤销逻辑。

## 目标

- 在系统设置的“访问”页维护拥有全租户访问权限的账号。
- 只有同时满足 `is_system_admin=true` 和 `can_access_all_tenants=true` 的用户可以使用该能力。
- 支持按邮箱授予、按用户 ID 撤销，并保持操作幂等。
- 禁止调用者撤销自己的全租户访问权限，避免失去后续管理能力。
- 为授予和撤销写入平台级审计日志。

## 方案

### 后端

新增独立的全租户访问账号列表、授予和撤销接口，不复用或修改现有系统管理员管理接口。三个接口在现有登录认证之上增加双条件权限校验，并通过 repository/service 分层读写 `can_access_all_tenants`。

列表接口返回分页结果。授予接口接受 `user_id` 或 `email`，重复授予返回成功但不重复写库。撤销接口接受 `user_id`，重复撤销返回成功；撤销自己返回业务错误。每次授予/撤销（包括幂等请求）均记录平台审计事件和目标账号信息。

### 前端

在系统设置“访问”分区增加“全租户访问账号”标签输入框，交互沿用现有系统管理员标签输入框：

- 标签值使用邮箱，映射表保存邮箱到用户 ID。
- 新增标签触发授予，删除标签触发撤销。
- 权限变化前弹出确认框。
- 请求失败后重新加载服务端状态，避免界面与数据库不一致。
- 当前用户不出现在可删除标签中。
- 仅当当前用户同时拥有两项权限时展示该控件。

### 安全与兼容

- 后端是最终授权边界，前端隐藏仅用于改善体验。
- 现有 `is_system_admin` 的 list/promote/revoke API、授权条件和 UI 行为保持不变。
- 不修改数据库结构和既有字段语义。

## 测试

- 中间件：双条件均满足时放行，任一条件不满足时拒绝。
- Repository/service：分页列表、授予、撤销、幂等和禁止自撤销。
- Handler：请求校验、错误映射、返回结构和审计详情。
- 前端：类型检查、构建检查，并回归现有系统管理员管理控件。
