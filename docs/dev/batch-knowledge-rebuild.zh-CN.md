# 批量重建知识

## 目的

当知识库大批量上传后出现多个解析失败文件时，操作者可按当前条件筛选文档，一次选择全部筛选结果，并异步提交批量重建。该功能位于独立分支 `feature/batch-knowledge-rebuild`，基于 `upstream/main`，不依赖 MySQL 或运维功能分支。

## 使用方式

1. 打开文档知识库，在“解析状态”中选择“失败”。
2. 进入批量管理，先勾选当前已加载的文档，或选择“全部 N 个筛选结果”。
3. 点击“重建知识”并确认。
4. 页面会显示已提交、跳过和未能提交的数量；最终结果以每个文档的解析状态和错误信息为准。

“全部 N 个筛选结果”只在有活动筛选条件时显示，避免把整个知识库误选为批量重建对象。该范围仅用于重建，批量删除会被禁用。

## 安全语义

- 重建会清理文档现有分块并重新解析，因此确认框明确说明此影响。
- 已处于 `pending`、`processing`、`finalizing` 的文档会在服务端被跳过，防止重复入队。
- 只读成员不能提交重建。服务端复用知识库、租户和 API Key 作用域校验。
- 选择全部筛选结果由服务端在目标知识库和授权上下文中解析，不由浏览器拼接跨分页 ID。
- 单次操作最多处理 1,000 个文档，每个维护队列任务最多处理 200 个文档；大操作会拆成多个低优先级任务，避免挤占上传和聊天请求。
- 单个文档重建失败不会阻断同批其他文档。提交成功只代表任务已入队，不代表所有文档已经重建成功。

## 接口

```http
POST /api/v1/knowledge/batch-reparse
```

兼容已有的明确 ID 调用：

```json
{
  "kb_id": "kb-123",
  "ids": ["knowledge-1", "knowledge-2"]
}
```

全选筛选结果使用服务端筛选快照：

```json
{
  "kb_id": "kb-123",
  "filter": {
    "parse_status": "failed",
    "tag_ids": ["tag-1"],
    "keyword": "invoice"
  }
}
```

响应包含 `task_ids`、`submitted_count`、`skipped_in_flight_count` 和 `enqueue_failed_count`。一次操作可能产生多个维护队列任务。

## 可观察性

每个维护队列任务会记录一条聚合审计事件 `knowledge.batch_reparsed`，其中包含任务 ID、文档数和失败数。批次内的单文档重建审计事件会被抑制，避免一次大批量操作淹没审计日志。

## 非目标

本功能不自动重试失败文档、不重新上传源文件、不修改解析配置，也不保留旧分块以供回滚。此类需求应作为单独功能讨论。
