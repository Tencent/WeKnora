# 依据目录、小节要求和正文构建素材知识地图

执行素材发现上下文对照实验的 C 组。只允许改变写作平台上下文，WeKnora 检索、证据核验、分类和输出协议必须与另外两组保持一致。

只筛选和呈现知识，不制定写作策略，不生成或修改正文。

## 输入

要求调用方提供：

- `kb_id`：WeKnora 知识库 ID。
- `output_dir`：本组独占的空输出目录。
- `node_ids`：可选；未提供时使用全部未忽略的二级小节。
- `max_queries_per_node`：可选，默认 `6`。
- `match_count`：可选，默认 `10`。

不要猜测 `kb_id`。如果 `output_dir` 已包含其他组或历史运行结果，停止并报告，避免实验污染。

## 严格限制写作上下文

调用一次 `writing_system.get_document_outline`，再对每个目标二级小节调用一次 `writing_system.get_section_content(node_id)`。

使用目录返回的文档标题、产品构想、行业、全文写作指导、章节和小节信息，以及小节工具返回的：

- `node_id`
- `title`
- `key_point`
- `content`
- `status`
- `updated_at`

所有 `node_id` 必须来自本次目录。

禁止调用或使用：

- `get_section_review`
- 启发式写作、正文评审及任何写回工具
- 其他组的输出文件

将实际可见的写作平台字段和值原样保存到 `context.json`，并标记 `context_group=full_content`。

## 固定的 WeKnora 协议

只使用：

- `list_knowledge`
- `get_knowledge`
- `get_wiki_build_status`
- `wiki_index_view`
- `wiki_search`
- `wiki_read_page`
- `hybrid_search`

不得上传、删除或修改 WeKnora 内容。

### 1. 冻结素材快照

分页调用 `list_knowledge`，直到取得全部素材。记录每份素材的 `knowledge_id`、标题、文件名、文件类型、`file_hash`、`updated_at`、启用状态、解析状态和摘要。

对可处理素材调用 `get_wiki_build_status`。只有 `ready=true` 时才使用其 Wiki；不得把解析完成当成 Wiki 完成。

调用一次 `wiki_index_view`，保存本轮 Wiki 导航快照。运行期间发现素材的 `file_hash`、更新时间或 Wiki 状态变化时，停止并报告快照已经失效。

### 2. 提取信息需求

依据允许的目录、小节要求和现有正文，为每个目标小节提取：

- 需要回答的问题；
- 需要的事实、数据、案例和反例；
- `key_point` 明确要求验证的判断；
- 正文中的数字、事实和强结论；
- 正文缺失、含糊、矛盾或使用占位符的信息；
- 可能存在的证据缺口。

将正文陈述视为待核验对象，不得默认正文正确，也不得为了贴合正文而降低素材关联性标准。

### 3. 使用三条发现路径

在 `max_queries_per_node` 总预算内自主分配下列检索路径，并在 `audit.json` 记录每次查询、目标小节和路径：

- 任务驱动：根据目录、小节要求、正文和信息需求调用 `wiki_search`，再用 `wiki_read_page` 阅读候选页。
- 素材驱动：逐份检查素材摘要及其可定位的 Wiki 内容，映射到相关小节。
- 证伪补漏：搜索正文结论的反证、冲突数据、限定条件和未覆盖需求。

三组必须采用同一个查询预算和 `match_count`。不要因为某条证据符合正文或预期就停止寻找反证。

### 4. 核验原始证据

Wiki 只用于发现和导航，不作为最终事实证据。

对每个准备收录的确定性知识点调用 `hybrid_search`，回到原始片段。记录：

- 原始 `knowledge_id` 和素材标题；
- 原文片段及 MCP 返回的定位信息；
- 命中查询；
- 证据能证明和不能证明的内容。

无法回到原始片段的候选标记为 `unverified`，不得列为强关联知识。Wiki 与原始片段不一致时，以原始片段为准并记录差异。

当前 WeKnora MCP 不能分页遍历单份文档的全部正文。必须区分 `metadata_only`、`wiki_examined`、`source_hit` 和 `unassessed`，不得把未命中等同于无关或声称已经完整阅读全文。

## 组织面向读者的知识树

不要按检索顺序、素材顺序、查询词或写作小节逐条堆放结果。先对已核验的强关联和辅助知识进行语义归并，再构建面向普通读者的主题树。

- 从素材实际内容中归纳 `4–8` 个一级知识主题，不预设固定分类。
- 每个一级主题下建立必要的二级子主题，通常不超过三层。
- 把表达同一事实的多个片段合并为一个知识点，把不同来源挂在该知识点下。
- 使用“主题 → 子主题 → 知识点 → 来源文档”的主结构。
- 不以来源文档或写作目录作为一级结构。
- 每个主题先用通俗语言说明“它是什么”和“为什么与本次写作任务相关”。
- 每个知识点标注可关联的写作小节，但把小节编号作为辅助索引。
- 冲突事实并列放在同一知识节点下，不要分别散落，也不要替用户裁决。
- 未核验候选和信息缺口集中放在文末，不要混入已核验知识树。
- 无关素材只出现在素材索引中，不进入知识树。

知识树总览采用以下形式：

```text
AlN 材料
├─ 工艺与材料性能
│  ├─ 高导热特性 [K-001]
│  │  ├─ 来源：[D-003] ××材料研究
│  │  └─ 来源：[D-007] ××产品手册
│  └─ 烧结与加工难点 [K-002]
│     └─ 来源：[D-004] ××工艺报告
└─ 市场与供应格局
   ├─ AlN ESC 市场占比 [K-003]
   └─ 海外供应集中度 [K-004]
```

总览只承担导航作用，随后展开详细知识树。每个知识点必须包含：

- **知识结论**：用一至三句话说明素材共同表达的内容。
- **与本次写作的关联**：说明为什么有用、可支撑哪些小节，以及不能证明什么。
- **来源依据**：列出文档 ID、标题、定位和最小必要原文片段。
- **适用边界与冲突**：说明数据条件、时效、口径和相反证据。

## 统一知识点格式

每个知识点只表达一个可独立核验的判断。使用下列稳定 ID：

```text
K-<knowledge_id前8位>-<source_location或excerpt_hash前8位>
```

在 `evidence.jsonl` 中逐行记录：

```json
{"evidence_id":"K-...","claim":"...","claim_type":"fact|inference|assumption","relation":"strong|supporting|unverified|unrelated|unassessed","target_nodes":["1.1"],"categories":["..."],"source":{"knowledge_id":"...","title":"...","location":"...","excerpt":"..."},"discovered_by":["task-driven"],"supports":"...","limitations":["..."],"conflicts":[]}
```

严格区分原文事实、综合推断、正文陈述和未知信息。每项关联性判定都写明理由。正文与素材冲突时并列呈现，不替用户消解冲突。

## 输出

只在本组 `output_dir` 写入：

```text
knowledge-tree.md
materials-index.md
context.json
evidence.jsonl
audit.json
```

### `knowledge-tree.md`

把它作为唯一的主要阅读入口，并严格按以下顺序组织：

1. **本次处理概览**：用不超过十行说明查看了多少份素材、核验了多少条知识、归纳出哪些主要主题，以及哪些内容受工具能力限制。
2. **知识树总览**：用紧凑文本树展示主题、子主题、知识点和来源文档。
3. **详细知识树**：按主题连续讲解；每个主题说明与写作任务的关联，每个知识点附来源、原文依据和适用边界。
4. **写作小节反向索引**：按 `node_id + 小节标题` 列出可用知识点 ID 和一句话用途，帮助写作者定位，但不重复完整知识内容。
5. **冲突与待确认事项**：集中呈现来源冲突、无法核验的候选知识和素材缺口。
6. **素材来源表**：列出 `D-xxx`、文档标题和其贡献的知识主题，供读者回查。

不要在主要阅读入口中展示查询日志、候选去重过程、大段 JSON、内部评分或工具调用细节。

### `materials-index.md`

展示全部素材的简洁表格：

```markdown
| ID | 素材 | 关联等级 | 贡献主题 | 覆盖状态 | 未采用原因 |
```

对无关、不可处理和未评估素材明确说明原因，避免静默遗漏。

### 审计附件

- `context.json`：记录本组实际可见的 writing_system 上下文、素材快照和实验参数。
- `evidence.jsonl`：保存用于跨组集合比较的规范化知识点。
- `audit.json`：保存查询、候选、去重、核验和取舍记录。

审计附件用于机器比较和追责，不作为普通读者的默认阅读材料。

不要读取、合并或评价其他实验组的结果。跨组比较由独立步骤完成。

## 完成条件

只有满足以下条件才报告完成：

- 全部素材均已进入台账；
- 每份素材都有覆盖状态；
- 每个强关联知识点都有原始证据；
 `knowledge-tree.md` 已按主题树聚合，主题、关联原因、知识结论和来源文档能够连续阅读；
- 所有输出均标记 `context_group=full_content`；
- 将正文视为待核验对象而非事实来源；
- 未产生写作策略或修改正文。
