# Brainstorm Summary

- Change: knowledge-scope-foundation
- Date: 2026-07-14

## 确认的技术方案

采用“一个业务系统对应一个 WeKnora 知识库 + 结构化知识范围”的方案。租户内设置一个默认部门公共知识库；系统查询默认组合部门公共知识、系统公共知识和所选业务版本专属知识。多系统查询为每个系统独立解析当前或显式选择的版本后再合并证据。

`system_id`、`system_version_id`、`scope_type` 和可选的 `project_id` 由后端统一 Scope Resolver 解析。RAG、Agent 工具和 Neo4j 查询均消费同一个已解析范围；标签只允许进一步缩小结果，不能承担隔离或扩大范围。一个系统版本可以关联多个项目，版本状态不冻结写入。

## 关键取舍与风险

- 所有用户可访问租户内全部系统，但每次查询必须显式或默认解析系统与版本范围，不能依赖提示词或模型判断隔离。
- `project_id` 仅用于可选筛选和来源追溯，不建立项目主数据，也不参与强制隔离。
- 部门公共知识独立存放，不复制进系统知识库，避免重复维护和版本漂移。
- 首期不建立跨系统 Neo4j 关系；联合分析先分别检索各系统范围内证据，再由 Agent 关联。
- 新能力使用功能开关和显式迁移，避免对既有数据作不可靠推断，并降低持续合并腾讯上游代码的冲突面。

## 测试策略

按 TDD 实施目录、范围解析、入库、RAG、Neo4j、Agent 和前端选择器。重点覆盖租户边界、错误系统/版本组合、默认版本解析、部门公共知识自动合并、标签不能扩大范围、跨系统联合查询、依赖失败与迁移失败。最终执行后端、前端和 Docker 端到端验证，并检查来源信息完整性。
