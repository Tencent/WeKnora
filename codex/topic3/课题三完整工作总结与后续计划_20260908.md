## 2. 我们为什么选择课题三

最开始，我们阅读了文件夹中的课题说明和提交流程文件，并比较了各个课题的实现难度、验收清晰度和时间风险。

你的明确要求是：选择最简单、最好实现、最稳妥的题目。最后选择课题三“质量评测基线与成本可观测”，主要原因是：

- 验收指标明确，可以用数据库记录、实验结果和 CI 输出证明。
- 很多能力可以在 WeKnora 原有评测流程上扩展，不必重新开发完整系统。
- 相比插件、沙箱、权限隔离等课题，工程风险更容易控制。
- 相比高度开放的课题，课题三更容易形成可复现、可量化的交付证据。

课题三需要解决的核心问题，被我们拆成了五块：

1. 评测结果必须持久化，重启后仍能查询。
2. 一次评测必须同时说明检索质量、回答质量、耗时和费用。
3. 模型管理页面必须能查看调用量、Token、缓存和费用。
4. Embedding 缓存和 Wiki 提示词结构优化必须有真实对照实验。
5. CI 必须能发现检索效果退化，并在正式配置后阻止不合格代码合并。

八种解析引擎横向比较属于扩展内容，本次明确不做，避免扩大范围。

## 3. 整体工作思路

### 3.1 先固定范围，再开始开发

我们把开发基线固定为与课题材料对应的 WeKnora `v0.7.2`，没有直接追随官方仓库后续版本。这样可以避免上游持续变化导致接口、数据库和前端反复调整。

固定方案包括：

- Windows 电脑运行 Docker Desktop，业务运行在 Linux 容器中。
- PostgreSQL 保存评测、模型用量和 Embedding 缓存。
- 在现有模型管理页面增加统计区，不创建第二套管理系统。
- 使用同一个阿里云百炼账号提供对话、Embedding 和 ReRank。
- 对话模型：`qwen3.7-flash-2026-07-15`。
- Embedding 模型：`text-embedding-v4`，1024 维。
- ReRank 模型：`qwen3-rerank`。
- 评测并发固定为 1，优先降低波动和付费风险。
- 先运行 1 题冒烟测试，再运行 10 题正式评测。

### 3.2 先做最便宜的验证

你多次要求“用最不消耗 Token 的方法”和“迅速解决”。因此我们一直采用以下顺序：

1. 先运行本地单元测试、语法检查、回归 fixture 和数据库检查。
2. 本地逻辑全部通过后，才进行一次最短真实请求。
3. 真实请求失败后立即停止并查日志，不盲目重复调用。
4. 先完成 1 题真实冒烟，确认完整链路，再运行 10 题。
5. 正式实验结束后冻结结果，不为了让数字“更好看”而反复重跑。

### 3.3 明确区分实现、验证和真实验收

整个过程中，我们把状态分为四级：

- 已实现：代码已经写好。
- 已本地验证：单元测试或本地逻辑测试通过。
- 已真实验收：真实 WeKnora、真实数据库和真实百炼调用通过。
- 待完成：尚未形成对应证据。

fixture、mock 或页面展示只能证明程序逻辑，不能代替真实模型实验。正式基线只能由人工检查后确认，脚本和 CI 都不能自动覆盖。

### 3.4 安全和证据原则

- API Key 只由你在页面或隐藏终端提示中输入。
- Key 不写入代码、结果文件、日志或 Git。
- `sk-` 开头的 WeKnora 本地 API Key 使用 `X-API-Key`。
- JWT 才使用 `Authorization: Bearer`。
- 费用字段缺失时写“未知”，不能假装为 0。
- 厂商缓存没有命中时如实写“未观察到”，不能宣称优化成功。
- 正式实验原始结果、正式基线和证据哈希冻结，后续不修改实验数值。
- 不向腾讯官方 `upstream` 直接推送，只推送到你的 Fork。

### 4.6 Embedding 持久化缓存

Embedding 缓存保存在 PostgreSQL。缓存键包含：

```text
租户 + 厂商/部署 + 模型配置版本 + 维度/关键参数 + 精确输入文本哈希
```

已实现并测试的行为包括：

- 相同文本再次处理时不重复调用厂商；
- 不同文本、模型或维度不会错误命中；
- 批量输入只请求未命中的部分；
- 最终向量按原输入顺序还原；
- 失败、空向量或维度错误不写入缓存；
- 单条、批量和带回调路径统一经过缓存；
- 缓存和统计可以独立开关；
- 冷缓存清理只删除当前租户、当前模型和当前实验文本对应的记录，不清空整张表。

### 4.9 运行中发现的问题及修复

一键实验不是一次就成功，主要经历了以下问题：

| 问题 | 原因 | 处理结果 |
|---|---|---|
| Windows 找不到 `npm` | Windows 子进程需要解析 `npm.cmd` | 修正命令解析，安全测试增加覆盖 |
| 恢复阶段连接被关闭 | 预检异常后仍执行服务恢复 | 保留恢复逻辑，修复真正的前置错误后重新运行 |
| “缓存关闭阶段没有真实 Embedding 请求” | 原评测路径复用了已索引数据，不能证明关闭缓存后真实请求 | 调整实验语义和验证，使关闭、冷、暖三类条件都能被真实调用证据区分 |
| optimized Wiki 提示词低于 1024 Token | 固定公共前缀长度不足隐式缓存技术条件 | 调整固定前缀并加入真实 Token 阈值检查 |
| GitHub 证据哈希校验失败 | Windows CRLF 与 Linux LF 导致同一文本的原始字节不同 | 改为文本 LF 规范化后计算 SHA-256，二进制仍按原始字节校验 |

这些修复都没有篡改实验报告数字，也没有把失败批次伪装成成功批次。

### 5.1 Embedding 缓存实验

正式实验共 9 轮：缓存关闭 3 轮、冷缓存 3 轮、暖缓存 3 轮。

| 条件 | 轮数 | 每轮真实 Embedding 调用 | 每轮本地命中 | Recall | MRR | 平均耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 缓存关闭 | 3 | 12 | 0 | 1.0 | 1.0 | 约 76.3 秒 |
| 冷缓存 | 3 | 12 | 0 | 1.0 | 1.0 | 约 90.7 秒 |
| 暖缓存 | 3 | 1 | 20 | 1.0 | 1.0 | 约 83.3 秒 |

结论：

- 暖缓存把三轮真实 Embedding 调用从 36 次降到 3 次，减少约 91.7%。
- 暖缓存三轮共处理 63 项输入，其中 60 项命中，输入命中率约 95.2%。
- 9 轮 Recall 和 MRR 都是 1.0，缓存没有破坏检索质量。
- 暖缓存耗时比冷缓存平均低约 8%，但只有 3 次样本，且受网络和模型服务波动影响，因此不能宣称稳定显著加速。
- 核心验收目标是减少真实调用和费用，这一点已经得到充分证明，不需要重做。

结果：

正确结论是：提示词结构优化已经完成，输出质量没有下降，但本次没有观察到百炼隐式缓存命中。公共前缀达到长度条件并不保证厂商一定命中。样本量也不足以证明 optimized 稳定变慢，因此不重复实验、不虚构收益。
