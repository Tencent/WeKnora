# RhinoCache 架构与可观测性规范

## 文档性质

本文描述一个用于教学验收的虚构系统 RhinoCache。文档不包含真实用户、真实业务、访问凭据或生产数据。系统的本地验收代号为 `RHINO-WIKI-CACHE-2026`。

## 系统目标

RhinoCache 用于验证知识库系统在重复处理相同语义内容时，能否减少不必要的模型调用，同时完整记录质量、成本和延迟。系统必须保证缓存优化不会改变检索结果、回答事实或租户隔离边界。任何性能提升都必须建立在正确性保持不变的前提上。

## Embedding 持久缓存

Embedding 缓存键由租户标识、模型标识、模型维度、规范化文本哈希共同组成。缓存不能仅以文本为键，因为不同租户和不同模型的向量不可互换。缓存记录保存在数据库中，因此服务重启后仍可复用。首次请求调用向量模型并写入缓存；后续相同请求直接读取缓存。缓存条目具有过期时间和容量上限，过期清理由后台任务执行。

缓存命中不得跨越租户。租户 A 和租户 B 即使提交完全相同的文本，也必须分别产生独立的缓存记录。模型版本、维度或关键参数变化后，旧向量不得继续命中。缓存层出现错误时应安全降级到真实模型调用，不能使文档处理失败。

## 模型调用记录

每次模型调用都应记录模型名称、模型类型、用途、输入 Token、输出 Token、缓存读取 Token、缓存写入 Token、缓存未命中 Token、估算费用、耗时和成功状态。普通问答、评测任务、Wiki 生成和后台文档处理使用同一套观测口径。

系统禁止保存 Prompt 正文和模型响应正文。稳定前缀只允许保存经过部署密钥保护的 HMAC 指纹；如果没有配置密钥，应省略指纹，而不是保存容易猜测的短哈希。记录按租户隔离，默认保留三十天。Provider 错误可能包含请求片段，因此模型调用表不保存原始错误文本。

## 评测闭环

每次评测都固定数据集、模型、分块参数和检索参数，并保存数据集指纹、模型配置指纹和代码版本。一次运行应同时产生检索准确率、答案质量、模型费用和端到端延迟。核心检索指标包括 Precision、Recall、MRR 和 NDCG；生成指标包括 ROUGE-L。

持续集成在拉取请求和每日计划任务中运行。如果 Recall 低于基线，门禁必须返回非零退出码，并在机器可读报告中指出失败字段 `metric.retrieval_metrics.recall`。评审者应能使用一条命令生成与终端输出一致的 JSON 报告。

## Wiki Prompt 缓存策略

Wiki 请求把长期稳定的系统规则放在消息最前面，把同一批文档共享的来源上下文放在稳定区域，把当前页面差异、当前操作和动态问题放在末尾。Provider 根据公共前缀识别缓存。稳定内容前置后，后续请求可复用已经计算的前缀，从而减少输入计算、降低首 Token 延迟和估算费用。

缓存统计必须使用 Provider 返回的字段，不能根据两次请求看起来相似就自行推断命中。报告分别展示缓存读取 Token 和缓存未命中 Token，并按 `cache_read_tokens / (cache_read_tokens + cache_miss_tokens)` 计算命中率。不支持缓存上报的本地模型应显示“不支持”或“未上报”，不能伪造为百分之零。

## 验收原则

验收分为正确性、隔离性、持久性、可观测性和性能五部分。正确性要求重复请求返回等价事实；隔离性要求缓存不跨租户；持久性要求服务重启后仍能命中；可观测性要求数据库和模型页面数据一致；性能要求在相同输入条件下比较 Provider 调用数、缓存命中率、费用和耗时。

所有实验资料必须保留。实验过程中不得删除知识库、文档、模型、数据库记录、容器、缓存或报告。若某个自动化命令会清理临时资源，应在执行前明确说明并选择不删除数据的替代方案。
