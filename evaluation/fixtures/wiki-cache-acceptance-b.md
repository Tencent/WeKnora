# RhinoCache 运行验收与优化记录

## 文档性质

本文是虚构系统 RhinoCache 的第二份教学验收材料，与《RhinoCache 架构与可观测性规范》描述同一系统。文档不包含真实业务数据。统一验收代号仍为 `RHINO-WIKI-CACHE-2026`。

## 重复入库场景

验收人员对同一组规范化文本执行两轮处理。第一轮缓存为空，Embedding Provider 需要计算向量；第二轮使用相同租户、相同模型、相同维度和相同文本，应直接读取持久缓存。两轮的请求文本数量保持一致，报告同时记录请求数量和真实 Provider 调用数量。

若第一轮请求一百段文本并产生一百次 Provider 计算，第二轮只有二十五段新文本，其余七十五段从缓存读取，则 Provider 调用减少七十五次，减少率为百分之七十五。这个数字只有来自真实计数器时才能作为测量结论；仓库中的示例 JSON 只能用于验证计算公式，不能冒充线上实验结果。

## 服务重启场景

完成第一轮后重启后端服务，但不删除数据库、缓存表或模型配置。重新发送相同文本，如果缓存持久化正确，第二轮仍能读取原向量。服务重启前后的向量维度必须相同，检索结果不能因为重启而变化。

## 租户隔离场景

租户一和租户二分别处理相同文本。每个租户的首次请求都需要独立调用 Provider，随后只能命中本租户的缓存。数据库索引应包含租户与模型维度，任何跨租户命中都被视为严重缺陷。统计页面也只能聚合当前租户的数据。

## Wiki 公共前缀场景

Wiki 生成会执行概念提取、页面摘要、页面合并、引用整理和首页生成。不同调用包含大量相同的系统约束，例如事实必须来自源文档、引用必须可追溯、页面结构必须稳定、动态操作必须放在末尾。旧的排列方式把变化内容插入前部，使 Provider 难以识别公共前缀。

优化后的排列把固定系统规则放在最前，把同批文档共享的来源上下文放在其后，把页面差异和当前请求放在最后。第一次请求建立缓存，紧随其后的相关请求复用前缀。缓存命中由百炼响应中的 `prompt_tokens_details.cached_tokens` 证明。只有 `cached_tokens` 大于零时，调用才被统计为实际命中。

## 真实测量要求

前测和后测必须使用同一模型、同一地域、同一知识库配置和相近时间窗口。报告至少包括调用用途、Prompt Token、缓存读取 Token、缓存未命中 Token、命中率、耗时和估算费用。为了避免缓存自然过期影响结果，两轮相关调用应连续执行。

短 Prompt 可能低于 Provider 的缓存阈值，因此未命中不代表代码失效。评测应选择包含足够稳定前缀的 Wiki 请求，并分别说明哪些调用超过阈值。不同用途的 Prompt 模板不同，不能把一个用途建立的缓存错误归因到另一个用途。

## 成本解释

模型页面使用用户配置的每百万 Token 单价估算费用。免费额度抵扣意味着实际账单可能为零，但估算费用仍用于比较优化前后的理论成本。报告应明确区分“估算原价”和“实际扣款”，避免把免费额度误解为模型调用没有资源成本。

缓存读取 Token 使用缓存命中单价，未命中 Token 使用标准输入单价，输出 Token 使用输出单价。价格配置必须遵循 Provider 对返回字段的计费口径：`0` 表示该类 Token 确实免费，不会自动继承普通输入单价。若隐式缓存的创建 Token 按标准输入价计费，应把“缓存创建”配置为标准输入单价；只有 Provider 明确不收费时才配置为零。币种不同的费用不得直接相加。

例如，阿里云百炼 `qwen3.7-plus` 在华北 2、单次输入不超过 256K Token 时，公开原价为普通输入 2 CNY/M、输出 8 CNY/M、隐式缓存命中 0.4 CNY/M；隐式缓存创建按普通输入价格计费，因此对应的缓存创建价格也是 2 CNY/M。实际价格以执行实验时的 Provider 官方价格页和控制台为准。

## 验收结论格式

最终结论必须同时回答四个问题：质量是否保持、Provider 调用是否减少、Wiki 缓存命中率是否提高、费用和延迟是否改善。每项结论都需要数据库记录、自动化测试或 Provider 返回字段作为证据。截图可以辅助说明，但不能替代可复现的结构化数据。

本次实验继续遵守不删除原则。新建知识库、上传文档和生成的 Wiki 页面全部保留，方便评审人员复查。所有报告使用明确的时间戳和模型名称，禁止使用无法追溯的手工百分比。
