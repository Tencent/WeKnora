# 跨会话长期记忆

长期记忆把同一个人过去的对话保留下来，供后续会话使用。数据按工作空间和调用者身份隔离，不同空间、IM 用户或嵌入访客分别维护个人记忆。

记忆分三层存放，各有自己的写入方式：

| 层 | 内容 | 写入方式 |
| --- | --- | --- |
| 画像 | 每人一份文档，带 `## ` 小标题，每轮对话都注入 | 后台从会话记忆整体改写，也可手工编辑 |
| 会话记忆 | 每段对话一份完整叙述：问了什么、用户自己纠正了什么、结论是什么、还有什么没定 | 对话安静下来后由模型写成 |
| 原话笔记 | 用户明确要求记住的句子，按原文保存 | 对话里说「记住……」即写入，也可手工添加 |

画像带 `revision`、`episode_count`（由多少段会话记忆改写而来）、`user_edited_at` 和 `generated_at`；会话记忆带 `title`、`slug`、`outcome`、`keywords`、`use_count` 等字段，取值见[记忆 API](../04-api/02-api-memory.md)。

## 开启长期记忆 {#开启和使用}

1. 空间 Admin/Owner 在「设置 → 长期记忆」开启空间开关，默认关闭。
2. 选择「仅明确记住」或「自动提取」；自动模式可指定抽取模型和画像改写模型，留空沿用对话使用的模型。
3. 个人记忆管理中可关闭自己的记忆，即使空间已开启也不会强制使用。
4. 在对话里明确说明要记住的偏好，或使用记忆管理手工添加；之后可在另一会话检查是否应用。
5. 画像正文可以直接改写，用来纠正描述得不准的部分；改动下一轮即生效。

| 模式 | 行为 |
| --- | --- |
| `explicit_only` | 只记录明确要求记住的内容，不运行后台 LLM 蒸馏 |
| `auto` | 额外在后台从对话写出会话记忆，并在同一次后台运行里改写画像 |

智能体的 `memory_enabled=false` 可单独禁用记忆读写，省略则继承空间设置。IM/Embed 使用所绑定智能体的记忆偏好；API Key 必须 full-access 才能使用个人记忆管理接口。功能受空间、个人和当前请求的开关共同约束。

## 管理记忆

| 操作 | 用途 |
| --- | --- |
| 编辑画像 | 直接改写常驻画像正文，最长 2400 字；改动会被记录，下一轮即生效 |
| 删除画像 | 清空画像，会话记忆保留，下次整理会重新生成一份 |
| 查看 / 删除会话记忆 | 按对话逐段查看完整叙述，删除不希望保留的那一段 |
| 新增 / 删除原话笔记 | 手工维护明确要求记住的句子，最长 300 字，每人最多 20 条 |
| 立即整理 | 立刻用最近的会话记忆重写一次画像，不等待后台整理 |
| 导出 / 清空 | 下载自己的 JSON 记忆，或清空自己的三层记忆 |

一段对话安静 12 分钟后写成会话记忆。如果你已经转去别的对话，那这段就算结束了，不必等满窗口——只要它还没有会话记忆，就会在后台下一次唤醒（最长 90 秒）时立刻写，所以新开一段对话时上一段通常已经记住了。一直在进行的对话不会无限期推迟，距上一份会话记忆满 2 小时会先按已有内容写一份，之后安静下来再改写。一段对话只有一份会话记忆：对话继续后就地改写，`slug` 保持不变，而不是追加一份新的。只要用户说过话就会写，包括只有一轮的对话——一句自我介绍正是画像最该记住的内容，而判断一段对话是否琐碎是画像改写时通览全部会话记忆才做得准的事。

画像在写下会话记忆的那一次后台运行里紧接着改写，所以只要一段对话记住了，画像就已经读过它。一次运行写下几段会话记忆也只改写一次画像。反过来说，没有新的会话记忆时后台不会改写画像，也就不会有模型调用——需要立刻改写就点「立即整理」。

手工编辑画像会记录下来，后台改写会被告知这份文档里有人工措辞，但一次改写替换的是整份文档，所以手写的段落会被下一次自动改写整体替换。原话笔记不经过模型改写，「记住：我只用中文」这类要求同步写入，下一轮对话即生效。

关闭个人开关会暂停使用，删除或清空会移除数据。接口中的字段与取值见[记忆 API](../04-api/02-api-memory.md)。

## 对回答和检索的影响

每轮对话注入三部分：常驻画像、全部原话笔记，以及与当前问题语义匹配的会话记忆节选（最多 2 段，每段约 420 字）。完整叙述不随轮次注入，智能体推理可主动搜索会话记忆与历史对话取回。记忆仅影响问题理解和资料选择，不扩展知识库访问权限。

`use_count` 是全系统唯一的保留信号：被读过的会话记忆留在画像索引里，长期没人需要的会淡出索引，它也决定超出上限时谁先被裁掉。

开启检索个性化后，画像中「用户画像」「用户偏好」两节用于改写查询，反复出现在多段独立会话里的关键词用于理解问题。对话时间线会显示记忆相关步骤。后台任务按会话保存游标和待处理状态续接，避免短时间连续发问导致提取遗漏。

## 排查记忆未生效的问题 {#排查}

| 现象 | 检查 |
| --- | --- |
| 没有使用记忆 | 空间开关、个人开关、智能体开关，确认是否换了空间或身份 |
| 自动提取未出现 | write_mode、抽取延迟/最短间隔、模型连接与后台任务 |
| 刚结束的对话没有会话记忆 | 仍停在这段对话里时需安静 12 分钟才写，转去别的对话后约 90 秒内写；对话里用户一句话都没说则不写 |
| 画像没有反映最近的对话 | 画像跟着会话记忆一起改写，所以先看这段对话有没有写成会话记忆；有一段会话记忆就会生成第一份画像 |
| 立即整理没有改变画像 | 查看返回的 skipped：`too_soon`（刚整理过）、`too_few_items`（会话记忆不够）、`model_unavailable`（模型不可达） |

## 空间配置

空间管理员可通过设置页维护记忆开关、提取模式和模型。配置保存在 `memory_config`，通过 `GET/PUT /tenants/kv/memory-config` 读取和更新，完整字段见[记忆 API](../04-api/02-api-memory.md)。

| 字段 | 说明 |
| --- | --- |
| `enabled` | 空间开关，默认 false |
| `write_mode` | `explicit_only` / `auto` |
| `extract_model_id` | 写会话记忆的模型，空值沿用对话模型 |
| `consolidate_model_id` | 改写画像的模型，空值沿用抽取模型 |
| `extract_delay_seconds` | 回答完成后延迟提取，合并短时间内的多轮消息 |
| `extract_min_interval_seconds` | 同一人的提取最短间隔，控制调用频率 |
| `extract_instructions` | 空间自己的提取规则 |
| `max_episodes` | 每个身份保留多少段会话记忆，0 使用默认 200，上限 500 |
| `interest_threshold` | 同一关键词要出现在多少段独立会话里，才算这个人反复关心的方向，默认 3 |
| `embedding_model_id` / `vector_recall` | 选择记忆召回的向量模型并开启语义召回；无模型时用词法匹配 |
| `retrieval_conditioning` | 允许记忆影响问题理解和文档排序 |

超出 `max_episodes` 后按「最少被读、最久未读、最早写入」裁剪，但画像还没读过的会话记忆不参与裁剪——那是这段对话的唯一副本。

抽取模型用于写会话记忆，画像改写模型用于归纳，向量模型用于匹配当前问题。记忆功能会增加对应的模型调用；模型被记忆配置引用时，删除模型会显示依赖详情。
